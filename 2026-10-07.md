## Finding 1: `@inlang/paraglide-js@2.26.0` is a URL-pattern routing optimisation with nothing to ship

**No draft, no PR from the publish itself.** Recorded because it is the level-1 hit of the day, because 14 install sites resolve onto it, and because *reading it* is what produced finding 2.

`@inlang/paraglide-js@^2` is the manifest spec with by far the widest reach — **14 install sites** — and it resolves to **2.26.0**, published inside the window. Both tarballs read file by file, excluding source maps.

**Twelve new files, all under `dist/compiler/runtime/`:** `url-pattern-cache.{js,d.ts}` and `url-pattern-index.{js,d.ts}` plus their tests, including a `url-pattern-index.differential.test.js` — upstream shipped an equivalence test against the linear scan. Changed: `localize-url.js`, `extract-locale-from-url.js`, `route-strategy.js`, `create-runtime.js`, `generate-static-localized-urls.js`, `create-server-file.js`, `services/env-variables/index.js`, `package.json`. **Nothing outside those paths changed** — in particular no file in the message-compilation or project-load path.

What it does: the `URLPattern` compile cache moves out of `localize-url.js` into its own module, and a prefix-trie **candidate index** replaces the full linear scan over `urlPatterns` and `routeStrategies`. Three things make it semantics-preserving, and all three are visible in the source rather than inferred from a release note:

- **Order is preserved.** `patternCandidates` returns `[...ranks].sort((a, b) => a - b)` — original array index. The comment says it outright: *"Specificity must never change precedence, including unconditional patterns."*
- **Anything it cannot reason about stays in the full scan.** `mandatoryPathSegments` returns `[]` for any pattern that is not a complete conservative root-relative grammar, and `buildPatternIndex` then adds that rank to `root.ranks` — unconditional. Malformed patterns are kept in the native scan *on purpose*, so a constructor error stays observable. Non-`http(s)` protocols bypass the index entirely.
- **Runtime mutation of the public config now invalidates the derived data.** A `routingConfigVersion` counter plus a reference/string snapshot check (`indexIsCurrent`) feeds three memos that previously keyed on the URL alone. `extract-locale-from-url.js` and `route-strategy.js` gained `cachedLocaleConfigVersion` / `cachedRouteConfigVersion` guards. This is strictly a **correctness improvement**: before 2.26.0, editing `urlPatterns` at runtime could return a stale cached locale for an unchanged URL.

One unrelated generator fix rides along, in both `create-runtime.js` and `create-server-file.js`:

```
- const importRegex = /import\s+[\s\S]*?from\s+['"][^'"]+['"]\s*;?/g;
+ const importRegex = /^\s*import\s+[\s\S]*?from\s+['"][^'"]+['"]\s*;?/gm;
```

Anchoring to line start stops the import-stripper from eating a mid-line or in-string `import … from "…"` out of the injected runtime. Deps: `@inlang/sdk` `^3.0.6` → `^3.1.0`, the only dependency change.

**Why nothing ships from this.** `grep -rn "urlPattern\|URLPattern" skills/` gives **two** hits, and both are safe: `json-format.setup.md:57` lists `urlPatterns` as a thing the strategy section covers, and `paraglide.setup.md:190` says *"The exact `urlPatterns` object shape varies by Paraglide minor — look it up in the Paraglide docs for the installed version before emitting it; do not guess the shape."* **That hedge is exactly right and 2.26.0 is why it was worth writing.** No skill claims anything about pattern precedence, caching, or compile-time cost, so there is no claim for this release to invalidate.

## Finding 2: Paraglide does not implement ICU `#`, and the skill teaches it in nine places

`skills/.../libraries/paraglide/rules.template.md` L199 — in the file the skill **installs into the user's repo as coding rules** — says:

> `#` is the count placeholder inside a plural/selectordinal branch — do not repeat the variable name there.

Measured on `@inlang/paraglide-js@2.26.0`, using the catalog the skill itself seeds:

| message body | `count = 1` | `count = 1234567` |
|---|---|---|
| `{count, plural, one {# like} other {# likes}}` | `"1 like"` | **`"1234567 likes"`** |
| `{count, plural, one {{count} like} other {{count} likes}}` | `"1 like"` | **`"1234567 likes"`** |
| `{count, plural, one {{count, number} like} other {{count, number} likes}}` | `"1 like"` | `"1,234,567 likes"` |

The compiled output is the proof, not the rendering:

```js
// messages/likes.js, `#` form and bare {count} form alike
if (countPlural === "one") return (`${i?.count} like`);
// same file, {count, number} form
if (countPlural === "one") return (`${registry.number("en", i?.count, {})} like`);
```

So the rule is worse than imprecise — it names the broken form and explicitly warns the reader off the variable name, when the fix is to use the variable name **with a formatter**.
