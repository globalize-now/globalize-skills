## The finding — a loader that supplies its own fallback silences the framework's

### How the run got here

Nothing published. (C) reconciled. (A) did not fire. (B) swept 18 manifest specs and 113 transitive edges and found nothing that moved. Item 23 has been sitting since 2026-08-28 with two thirds open, and the 2026-09-06 report named it explicitly as the oldest.

### vue-i18n — what the loader does

`frameworks/vite/vue/vue-i18n.setup.md` ships `src/i18n/poLoader.ts`, the build-time Vite plugin that turns `.po` catalogs into vue-i18n message trees. Nuxt and Quasar both instruct the operator to copy that body **verbatim**, so it is the single source of truth for all three PO stacks. Its per-entry line was:

```ts
const value = entry.msgstr[0] || msgid   // fall back to source text if msgstr empty
```

The comment is wrong, and the wrongness is the bug. In this catalog scheme the `msgid` is the **call-site key** (`HomePage.title`) — the source text lives in the *source locale's* `msgstr`. The loader transforms one `.po` at a time and never sees the source catalog, so `|| msgid` cannot mean "source text". It means "the key".

### What actually happens — run, not read

Both loader bodies were **extracted back out of their own markdown** (`main`'s and the branch's), written to `.mts`, and driven through the plugin's own `transform` hook against a two-entry `en.po` / `fr.po` pair with `fr` fully untranslated. Same harness, same fixtures; only the extracted block differs. `vue-i18n@11.4.10`, `gettext-parser@9.1.1`, `vue@3.5.22`.

| | `main` (block 1640 B) | branch (block 1993 B) |
|---|---|---|
| `fr` tree | `{"HomePage":{"title":"HomePage.title"},"Common":{"right__ctx_direction":"Common.right"}}` | `{}` |
| `fr t('HomePage.title')` | **`"HomePage.title"`** | `"Welcome back"` |
| `fr t('Common.right__ctx_direction')` | **`"Common.right"`** | `"Right"` |
| console | **nothing at all** | `[intlify] Not found … Fall back to translate … with 'en' locale.` |
| `en` side | `"Welcome back"` | `"Welcome back"` |

Three things the fixtures establish that reading the loader could not:

1. **The page renders the raw key**, not the source text the comment promises.
2. **It defeats `fallbackLocale`.** `libraries/vue-i18n/setup.shared.md` configures `createI18n({ fallbackLocale: sourceLocale, … })` four steps later. That mechanism fires on a *missing* key. `|| msgid` makes the key present, so vue-i18n has nothing to fall back from and — crucially — **nothing to warn about**. The control run emits zero console output.
3. **The `msgctxt` case is worse.** The fallback value is the *unmangled* msgid (`Common.right`), not even the mangled key the call site uses (`Common.right__ctx_direction`).

The empty-catalog edge was checked rather than assumed: a fully untranslated catalog now transforms to `{}`, and driven through the shipped `setLocale()` shape — `createI18n({ messages: { en } })` then `setLocaleMessage('fr', {})` — `availableLocales` becomes `['en','fr']`, so the `!availableLocales.includes(locale)` lazy-load guard does not re-fetch. Partial catalogs behave per key.

### What it silently falsified

`libraries/vue-i18n/convert.shared.md` L561 tells the operator, as a verification step: *"Pick a target locale; the UI re-renders and falls back to source text for untranslated entries."* On the JSON path that holds, because the convert phase copies source text into every target key. **On the PO path it did not** — and the same convert phase copies source text into the target `msgstr` too, which is exactly why the repo's own fixture never reaches the empty case. The claim was true of the flow the skill drives and false of the flow a TMS round-trip produces. The line needed no edit; the fix makes it true.

### Lingui — the claim held, the paragraph beside it did not

Item 23's Lingui third was **verified correct**. Run with `@lingui/cli@6.6.0` + `@lingui/format-po@6.6.0`:

- `<Trans context="direction">Right</Trans>`, `<Trans context="correctness">Right</Trans>` and a bare `<Trans>Right</Trans>` extract as **three** entries with distinct ids — `zDbO5m`, `TqDA0I`, `nOPbWJ` — cross-checked against `generateMessageId()` from `@lingui/message-utils`. `libraries/lingui/rules.template.md` § `context` for disambiguation is right.
- `@lingui/format-po` writes `msgctxt` after the `#:` reference and directly above `msgid`, exactly as `skills/lovable-i18n/SKILL.md` L1366 says.

What the same fixtures exposed is the § PO catalog maintenance protocol two paragraphs down. Its contract is *"so your entries match what `lingui extract` produces — then CI's first run normalizes rather than fights your work"*, and it shows `msgstr ""` under the heading *"This is exactly what `lingui extract` writes with this project's config"*. With that config (`sourceLocale: 'en'`, `formatter({ lineNumbers: false })` — A3, unchanged), the extractor writes:

```
locales/en/messages.po        locales/fr/messages.po
msgid "Dashboard"             msgid "Dashboard"
msgstr "Dashboard"            msgstr ""
```

Measured across all four shapes the protocol covers — plain, `comment=`, `context=`, ICU plural — the source-locale `msgstr` equals the msgid **byte for byte**, `{count, plural, one {# item} other {# items}}` included.

**And it does not heal.** A real extractor-written `en/messages.po` was blanked by hand and re-extracted: every `msgstr` came back still `""` (only the header gained `Project-Id-Version`, `Plural-Forms` and friends), and the statistics table prints `-` rather than a count in the source locale's `Missing` column in both states. Nothing renders wrong — `lingui compile` emits the msgid as the value either way, `{"7p5kLi":["Dashboard"], …}` — which is why this survived. The file's promise holds for `#.` / `#:` / ordering and fails for exactly one field, in exactly the file the agent writes first.
