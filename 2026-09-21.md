## The finding — the `_locales` bridge fails silently, and every gate that could see it is blind

**→ [#86](https://github.com/globalize-now/globalize-skills/pull/86), ready for review.**

The standing order says a fully quiet run is the run that owes its whole budget to (F). The queue head, set on 2026-09-18, was *"the webext pair's `build-locales.mjs` claims (the four `ext_*` ids each with a description, and the web-ext lint claim), neither of which this log has ever run."*

Both claims survive. The script does not.

### Running claim 1

Four `msg({ id: 'manifest.*', message, comment })` descriptors copied verbatim out of Step 6, a `lingui.config.ts` copied verbatim out of Step 4, `@lingui/{core,cli,format-po,babel-plugin-lingui-macro}@6.7.0`, a real `lingui extract`, and the Step 7 script **extracted programmatically from the markdown** rather than retyped.

It works. `public/_locales/en/messages.json` carries `extName`, `extShortName`, `extDescription`, `extActionTitle`, each with a `description` holding that descriptor's `comment:` text, and the `js-lingui-explicit-id` marker stripped out of it — which is what the Step 3 `pofile` note claims. **Claim 1 verified.**

(Along the way, a hypothesis that had to be discarded: Lingui does *not* put `#.` extracted comments in `extra.translatorComments`. `comments` is the right field and the script reads the right one. Item 28 — the mechanism read from source predicted the wrong thing, and running it settled it in the reassuring direction for once.)

### The defect, found by getting the config wrong first

The first tree was built with `formatter({ explicitIdAsDefault: true })`, because that is the obvious way to get a PO whose msgid is the explicit id. It produced:

```
[build-locales] No "manifest.*" messages in src/locales/en/messages.po. Run `lingui extract` after editing src/i18n/manifest-strings.ts.
[build-locales] Wrote 2 locale file(s) to public/_locales/.
RC=0
$ cat public/_locales/en/messages.json
{}
```

That is not a misconfigured test rig. It is the bug.

`formatter({}).parse()` keys the catalog by message id **only when the PO carries Lingui's `#. js-lingui-explicit-id` marker**. Step 4's `formatter({ lineNumbers: false })` emits the marker, so the keys are `manifest.name`, `manifest.description`, … With `explicitIdAsDefault` the marker is absent, the keys are content hashes, and the explicit id moves into the entry's `message` field:

| `lingui.config.ts` | marker in PO | `formatter({}).parse()` keys |
|---|---|---|
| `formatter({ lineNumbers: false })` — Step 4 verbatim | yes | `manifest.name`, `manifest.description`, `manifest.short_name`, `manifest.action_title` |
| `+ explicitIdAsDefault: true` | **no** | `byhlWJ`, `NdlFEf`, `OFoI1j`, `TrDPVV` |

`Object.keys(source).filter((id) => id.startsWith(ID_PREFIX))` then matches nothing, the `console.warn` fires, **and the script continues** — `rm -rf public/_locales`, `{}` per locale, `Wrote 2 locale file(s)`, exit 0. The warning it does print misdiagnoses the cause: it tells the reader to run `lingui extract`, which has already run correctly.

`explicitIdAsDefault` is a legitimate `@lingui/format-po` option that this skill never sets. It gets there through Step 4's own instruction — *"If a `lingui.config.* ` already exists, reconcile rather than overwrite"* — on exactly the kind of project that already uses explicit ids. The coupling was written down nowhere, so there was nothing to reconcile against. **Item 34**: a config setting the guidance depends on is part of the guidance, and this is the sharpest instance yet, because the setting lives in a *third-party* config the skill tells you to preserve.

### Running claim 2 — and it is why this matters

*"`web-ext lint` does not catch an unresolvable `__MSG_` reference."* **True, and worse than the file says.**

`web-ext@10.6.0` (still `latest`, published 2026-08-04), two fixtures: identical MV3 manifests with `__MSG_extName__` / `__MSG_extDescription__` / `__MSG_extActionTitle__`, one with `_locales/en/messages.json` = `{}`, one with the four real messages. **The JSON reports are the same** — 1 error `ADDON_ID_REQUIRED`, 1 warning `MISSING_DATA_COLLECTION_PERMISSIONS`, the two Firefox-only findings the add-on already documents, and nothing else. A third fixture using `"manifest.name"` as a Chrome message name (a `.` is outside `A-Za-z0-9_@`) also lints clean. **Both parts of the claim verified.**

Then the composite, run verbatim out of `setup.add-ons.md`:

```
$ node check-webext-lint.mjs fx-empty
web-ext lint: 0 i18n finding(s) in fx-empty
EXIT=0
```

The add-on this repo installs into the user's CI reports a clean i18n gate on an extension whose entire store listing is blank. Its `I18N_CODES` filter is correct; there is simply nothing in the report to filter. **Item 21, in a CI check this repo ships** — and item 33, which says exactly that a CI check this repo installs is a shipped claim.

The full blindness chain, each link measured rather than reasoned about: the bridge exits 0 → `web-ext lint` is silent → the skill's CI helper exits 0 → `libraries/lingui/setup.add-ons.md`'s `localesBridgeScript` check asks whether the script is on disk and wired, and both are true. Only the convert phase's verify subagent (`SKILL.md` §3.5, webext checks 2–3) resolves `__MSG_x__` against the catalog — and it runs **once**, while the bridge runs on every `dev`, `build` and `zip`.

### The fix

1. **`manifestIdOf(key, entry)`** takes the key when it carries the prefix and falls back to `entry.message`. `readCatalog` becomes `readManifestEntries`, returning a catalog re-indexed by id — which also removes an unstated assumption that the hash key is stable across locales, rather than leaving it true-but-unargued.
2. **Fail closed**, and *before* the `rm -rf OUT_DIR`, so a failed run leaves the previous `_locales/` intact instead of replacing it with empty files. The message names both real causes.
3. **Write the coupling down** — Step 4 gains a paragraph on `explicitIdAsDefault` and an instruction not to "simplify" the id resolution back to one spelling; Step 7's intro states the fail-closed behaviour and why `web-ext lint` cannot be the gate. The `pofile` note's "marker already stripped" claim is **true and kept**, now scoped to the comments, since the marker's presence does change the keys.

**Deliberately not done** (item 20), and named in the PR rather than silently omitted: setting `explicitIdAsDefault` in the skill's own config (it rewrites every msgid — a TMS decision); giving the *setup* phase its own `_locales` acceptance step (§3.5 owns that at convert time; whether it should be duplicated is a question about where verification belongs); teaching `check-webext-lint.mjs` to resolve `__MSG_` (that is re-implementing §3.5 check 2 inside a CI helper).

**Why a PR and not an issue:** the defect, the fix, and the fix's validation were all produced by commands.

- **The parser diff is one hunk.** `IDENTIFIER_PREFIX_RE` becomes `createIdentifierPrefixRegex()`: compile `/([^\p{White_Space}\p{Pattern_Syntax}]*)/yu`, *check it actually matches* (`regex.exec("a ")?.[1] === "a"`), and fall back to a precomputed literal character class on throw or wrong answer. An engine-compat guard for runtimes without working Unicode property escapes — and notable in its own right as upstream applying item 41 to its own instrument.

Measured, not inferred (item 28): ten ICU messages — interpolation, plural (`one`/`other`), select, selectordinal, `date, medium`, `number, percent`, and non-ASCII argument names (`café`, `日本語`) — formatted through `new IntlMessageFormat(msg, 'en').format(values)` on Node 22 at **12.1.0** and at **12.1.2**. **Output identical, line for line.** The fallback never engages on an engine that has `\p{…}`.

And the consumer: the `messageCompiler` snippet from `vue-i18n/setup.shared.md`, dropped verbatim into a tree with `intl-messageformat@12.1.2` + `vue-i18n@11.4.12` + TypeScript 5.9.3 under `strict` — `tsc --noEmit` **rc 0**. v12's `IntlMessageFormat<V extends MessageValues | undefined = undefined>` defaults to the untyped `format` overload, so the shipped `formatter.format(ctx.values) as string` is untouched by the new type surface, and #83's "types-only major" framing holds at 12.1.2.

**Nothing to change.** The artifact is the measured comment on [#71](https://github.com/globalize-now/globalize-skills/issues/71#issuecomment-5756299226), the issue that predicted this class of movement — recorded because a check that only speaks when something is wrong is indistinguishable from a check that is not running.
