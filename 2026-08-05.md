### `next-intl@4.13.5` characterization

Release note (GitHub Releases, tag `v4.13.5`, 2026-08-04):

> **Bug Fixes** — Deprecate `setRequestLocale` and add blog post on `next/root-params` (#1632) — @amannn

Registry facts (verified via `curl` against `registry.npmjs.org`):

- **engines:** absent (unchanged).
- **peerDependencies:** `next ^12 || ^13 || ^14 || ^15 || ^16`, `react ^16.8 || ^17 || ^18 || >=19-rc || ^19` — **byte-identical** to 4.13.4. The Next.js peer floor did **not** move; `next/root-params` is a Next 16.3 feature but next-intl still supports back to Next 12.
- Only internal siblings bumped: `use-intl`, `icu-minify`, `next-intl-swc-plugin-extractor` → `^4.13.5`. `^4` pin admits it.

What the deprecation means (per the migration blog, `next-intl.dev/blog/nextjs-root-params`, 2026-08-04):

- Next.js 16.3 adds `next/root-params`, letting Server Components read top-level dynamic segments (like `[locale]`) natively. next-intl can now resolve the locale in a single place — `i18n/request.ts`, via `rootParams.locale()` — which makes `setRequestLocale` unnecessary for static rendering **on Next 16.3+**.
- Migration is a one-file change in `i18n/request.ts` (read `await rootParams.locale()`, validate, `notFound()` on miss), after which `setRequestLocale(locale)` calls can be removed from pages, and manual `getTranslations({locale})` overrides can drop the `locale` arg.
- **Caveats to carry into any skill edit:** (1) `next/root-params` does **not** work in Route Handlers or Server Actions — those still need an explicit `locale` override. (2) It requires **Next.js 16.3+**; below that, `setRequestLocale` is still the mechanism. (3) A pass-through `app/layout.tsx` must be removed (use `global-not-found` instead) so `app/[locale]/layout.tsx` qualifies as the root layout. (4) `generateStaticParams` is still required for static rendering.
