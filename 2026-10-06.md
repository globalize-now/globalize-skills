## Finding 1: `intl-messageformat@12.1.3` is a real parser fix the skills already receive

**No draft, no PR.** The manifest's range is correct; nothing to change. Recorded because it is the first level-1 hit in days and because *why* it needs no action is the useful part.

`intl-messageformat@^12` appears at three install sites — `nuxt/vue-i18n.setup.md:19`, `quasar/vue-i18n.setup.md:18`, `vite/vue/vue-i18n.setup.md:18` — and in three manifest stacks. It resolves to **12.1.3**, published inside the window.

**Read the tarballs, both versions, file by file.** The entire diff of `intl-messageformat` 12.1.2 → 12.1.3 is its own `package.json` version, the exact dep `@formatjs/icu-messageformat-parser` `3.5.20` → `3.5.21`, and the same one-line change carried in its bundled `intl-messageformat.iife.js`. The parser's own 3.5.20 → 3.5.21 diff is **one function**, excluding the source map:

```
2022c2022,2023
< 		if (this.message.startsWith(prefix, this.offset())) {
---
> 		const offset = this.offset();
> 		if (this.message.slice(offset, offset + prefix.length) === prefix) {
```

That is `Parser.bumpIf(prefix)`, whose thirteen call sites carry the one- and two-character tokens the ICU grammar turns on: `"/>"`, `">"`, `"</"`, `","`, `":"`, `"="`, `"{"`, `"+"`, `"-"`.

**The reason, from the upstream commit rather than a release title** — `formatjs/formatjs@6b3869a0b0`, 2026-10-05T11:07:54Z, *"fix(@formatjs/icu-messageformat-parser): tolerate MicrosoftAjax startsWith override (#7549)"*, fixing #7531:

> MicrosoftAjax replaces `String.prototype.startsWith` with a version that ignores position, breaking rich-text tags and ICU arguments. Compare tokens with `slice()` at the parser offset instead.

The commit adds regressions that monkey-patch `startsWith` to the position-ignoring form and assert parse equality across tags, ICU arguments and malformed input, plus one `IntlMessageFormat` end-to-end repro (`'Read our <link>Cookie Policy</link>.'` → `'Read our [Cookie Policy].'`). So the failure is real, specific, and **runtime-only** — it needs a page that loads MicrosoftAjax (ASP.NET ScriptManager) to manifest.

**Why nothing ships.** All three sites pin `^12`; `^12` resolves to 12.1.3; the fix arrives for anyone who installs today. No site pins an exact version, and no skill makes a claim about parser internals that 12.1.3 invalidates — `grep -rn "intl-messageformat" skills/` gives 23 hits, every one of them about *wiring* the compiler, not about how it parses.

**One thing a human may want to know, stated and not acted on.** Two tracked packages pin the parser's **previous major**: `@globalize-now/paraglidejs-po-format@0.1.2` → `@formatjs/icu-messageformat-parser@^2.11.4` (**this org's own package**) and `@ts-intl/eslint-plugin-ts-intl@2.0.0` → `^2.1.14`. Both parse at build time, where no MicrosoftAjax exists, so the bug cannot reach them — which is why this is a note and not a finding. Whether the first-party package should be on `^3` is a product call, not a library-check one.

### What is wrong is next door

**Three codes fire as errors and are absent from the table.** All three are already in the `I18N_CODES` set the emitted CI script gates on, so the skill ships a gate that fails a build on conditions its own "verified" catch list never mentions.

- `NO_MESSAGES_FILE_IN_LOCALES` — `_locales/fr/` holding only a `README.txt`: **error, "Empty language directory"**. A *wholly* empty `_locales/fr/` reports **nothing** — the scanner enumerates files, not directories. Both halves measured; the distinction is in the patch because it decides whether a reader believes the row.
- `NO_PLACEHOLDER_CONTENT` — `placeholders: {"x": {}}`: **error**.
- `INVALID_PLACEHOLDER_NAME` — `placeholders: {"y!": {...}}`: **error**.

**`INVALID_MESSAGE_NAME` cannot fire.** `addons-linter@10.13.0` declares and exports it (`'String name contains invalid characters'`) and never raises it: walking every occurrence of the identifier in `dist/addons-linter.js` gives **four hits, all inside the declaration block, zero reference sites anywhere else**. The contrast is what makes it a measurement rather than a guess — the same walk gives `PREDEFINED_MESSAGE_NAME` four declaration hits **plus one raise site**, and `NO_PLACEHOLDER_CONTENT` / `INVALID_PLACEHOLDER_NAME` one each. `NO_MESSAGES_FILE_IN_LOCALES` is raised through a factory (`messages.noMessagesFileInLocales(path)`), which is why a naive identifier count would have called it dead too — checked, and it is live.

### The patch keeps the dead code on purpose

`INVALID_MESSAGE_NAME` stays in `I18N_CODES`, annotated, rather than being deleted. Filtering on a code that is never emitted is a no-op today, and leaving it means the gate covers the condition for free if upstream wires the message up. Deleting it is the tidier diff and the worse gate. It is the one judgement call in the change and it is stated as such in the draft.
