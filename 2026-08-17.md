### Why the severity floor moved up

`rules.template.md` carries frontmatter `template: next-intl`, `templateVersion: 1`, `conditions: [router, localeNavigation, catalogFormat, paramsShape]`, and a token budget of 240 (App Router) / 200. Per `CLAUDE.md`, setup renders it against the project's real values and writes the result to `.agents/globalize-rules.md`, bridged from both `CLAUDE.md` (a real `@` import) and `AGENTS.md`. That file is **always-on context for every future session in the user's repo**.

So the three `setRequestLocale` rules at L160/197/207 are not advice the agent reads once during setup — they are standing instructions installed into user projects. On Next.js 16.3+ they instruct the agent to keep writing a call next-intl has deprecated. Nothing breaks (deprecation warning, not removal; `^4` admits it), but the blast radius is per-project and persistent rather than per-setup-run.

### Why the fix is bigger than the draft says

The old draft's proposal — "add a Next.js 16.3+ note, re-frame the existing guidance as required for < 16.3" — works fine for the two `.setup.md` / `.convert.md` prose files. It does **not** work as written for `rules.template.md`, because the rendered output has no runtime version check: whatever renders, ships. Presenting both paths in one rendered file would burn budget on a branch that cannot apply, which is precisely the cost `CLAUDE.md` says the template track exists to avoid.

The template's own format spec already prescribes the right shape. `references/rules-template-format.md` L154 documents this exact situation:

> **When a block genuinely depends on two axes, resolve them into one composite key** rather than reaching for nesting.

and gives `paramsShape` (`"promise"` / `"sync"` / `"none"`) as the worked example — the key that collapsed "App Router *and* Next 15+" into sibling blocks. The root-params migration is the same shape one Next major later ("App Router *and* Next 16.3+"), and it is **coupled to `paramsShape`**, since resolving locale via `await rootParams.locale()` in `i18n/request.ts` is what removes the need for the `params`-then-`setRequestLocale` dance those blocks teach. The refreshed draft therefore proposes a new composite condition key (working name `localeSource`, resolving to `"root-params"` / `"request-locale"`), added to the template's `conditions` list and to whatever setup step resolves condition values, with `templateVersion` bumped.

**Naming and exact resolution logic are left to the implementer** — this run is a check, not a design decision, and `localeSource` is a suggestion for the issue to argue with, not a conclusion.
