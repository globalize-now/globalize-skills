## Finding 1: `1.16.13` closes the "wait or pin" question, and opens a macOS one

**→ [draft 24](./pending-issues/24-swc-core-1-16-12-native-binding-cache.md) § "`1.16.13` answers the wait-or-pin question" and [draft 25](./pending-issues/25-next-intl-swc-native-binding-troubleshooting.md) § "Refreshed 2026-10-01", with the patch regenerated. Unfiled — no token.**

### The measurement

```
$ diff <(cd x1.16.12/package && find . -type f | sort | xargs sha256sum) \
       <(cd x1.16.13/package && find . -type f | sort | xargs sha256sum)
```

One of fourteen files differs, and `python3 -m json.tool` on both shows the whole difference is `version` plus the twelve pinned `optionalDependencies`.

| | `1.16.2` | `1.16.12` | `1.16.13` |
|---|---|---|---|
| `index.js:66` unguarded `require("./binding")` | present | present | **present, byte-identical** |
| `@swc/core-linux-arm64-gnu` unpacked / files | 33 325 239 / 4 | 10 664 616 / 4 | **10 668 712 / 4** |

The load probe used a hand-built tree (both registry tarballs, no `npm`) so that the result could not be an install artefact, and the **control at `1.16.2` by the identical method loads and `transformSync('const a=1;')` returns `"const a = 1;\n"`**. The `1.16.13` throw is `Failed to load native binding` with `cause[1]` = `ERR_SWC_NATIVE_CACHE: SWC native addon: validate cache root …/.cache: cache root has a parent writable by another user without trusted sticky protection` — the same predicate, reached the same way.

### The predicate, read from source

Three previous reports described this from `strings` output. `crates/swc_native_addon/src/platform/unix.rs` at `v1.16.13`:

```rust
fn cache_ancestor_is_secure(mode: u32, owner: u32, current: u32) -> bool {
    if owner != current && owner != 0 { return false; }
    mode & 0o022 == 0 || mode & STICKY_BIT != 0
}
```

applied to `root.ancestors()` — every ancestor, not just the root. Two corrections to how the drafts had it, both now fixed in them:

1. The `0o700` requirement belongs to `private_directory`, i.e. the **per-user namespace created under** the root, not the root itself. A `0755` user-owned `~/.cache` is fine. Earlier phrasing implied otherwise.
2. The default root is `$XDG_CACHE_HOME` if absolute, else **`$HOME/Library/Caches` on macOS** and `$HOME/.cache` elsewhere, and a `noexec` mount is rejected separately by `executable_cache_root`. Every previous version of both drafts named only the Linux path.

### The macOS routing change

Eight commits between the tags. The substantive one is `0b151bf`, and its only non-test production change is three words:

```diff
-    if *mode == CacheMode::Temporary {
+    if cfg!(target_os = "macos") || *mode == CacheMode::Temporary {
         return None;
     }
```

In `initialize()`, `replacement_carrier` returning `Some(carrier)` sends the load through `replacement::try_replace` and **`cache::materialize` is never called**, so `secure_cache_root` never runs. Returning `None` routes it to `cache::materialize` → `cache_directory` → `secure_cache_root`.

So until `1.16.13`, a writable macOS installation bypassed the ancestor predicate entirely via APFS self-replacement. From `1.16.13`, every macOS first load goes through it. Upstream's new `docs/native-addon-macos-startup.md` shows why — 17–18 % off first load across six rounds on two Node versions, installed-second-load median from ~255 ms to ~18 ms — and on an ordinary Mac the default `$HOME/Library/Caches` chain validates, so this is a straight improvement there. But the predicate is load-bearing on macOS for the first time: a Mac with `XDG_CACHE_HOME` on a shared or network volume, or under a directory owned by another non-root uid, can now fail where `1.16.12` succeeded. **The affected class is still narrow. It is no longer Linux-and-containers only, which is what every previous run asserted.**

### What this settles

- **"Wait for upstream to back it out" now has one data point against it and none for it.** The first release after the repackaging deepens reliance on the cache and leaves the unreachable-fallback bug in place. Three releases, three times unguarded.
- **Draft 25's `1.16.2` pin is re-confirmed, not superseded.** `~1.16.0` now resolves to `1.16.13`; `1.16.2` is still the newest release in that range shipping a real addon. The patch was **regenerated** (now **+78/-0**, was +70/-0) so it no longer asserts that `1.16.12` is current `latest`, and it names the macOS path and the `noexec` case.
- **A corollary that caught a latent error in draft 24's own prose:** `~1.16.2` is `>=1.16.2 <1.17.0`, so it admits `1.16.12` and `1.16.13` and resolves to **`1.16.13`**. Draft 24 had been citing `~1.16.2` as "the obvious change that is wrong because it pins backwards"; it is wrong for a second and simpler reason — it does not pin at all. Only the exact `"1.16.2"` that draft 25's `overrides` block uses does. Fixed in 24.
