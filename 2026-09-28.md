## Finding: the ICU `messageCompiler`'s defensive fallback does not fall back, and cannot see the case its comment names first

**→ draft [`23-vue-i18n-oncompile-error-fallback-unreachable.md`](./pending-issues/23-vue-i18n-oncompile-error-fallback-unreachable.md) + [`.patch`](./pending-issues/23-vue-i18n-oncompile-error-fallback-unreachable.patch). Unfiled — no token. Verified and ready to push.**

This is the (F) head carried since 2026-09-23: *the `vue-i18n` `messageCompiler` `onError` path.*

The skill emits, at `libraries/vue-i18n/setup.shared.md` L268–276 and again (uncommented) at `frameworks/nuxt/vue-i18n.setup.md` L147–151:

```ts
if (typeof message !== 'string') {
  // Defensive fallback: … fail loudly rather than silently mis-render.
  onError?.(new Error(`[i18n] ICU compiler requires string messages (key: ${key})`) as CompileError)
  return () => key
}
```

**`return () => key` never runs.** `@intlify/core-base@11.4.12` `getCompileContext()` (L1794–1821) wraps the host's `onError` and ends with `throw err` **outside** the `NODE_ENV !== 'production'` guard — a dev build throws a `SyntaxError` with a code frame, a production build re-throws the raw error, and both abort the call. `translate()`'s own recovery (`let occurred = false; … if (occurred) return format`, L1529–1539) is written for an `onError` that returns, so it is unreachable through this path too.

**Measured, not only read** — `@intlify/core-base@11.4.12` + `intl-messageformat@12.1.2`, `createCoreContext({ messageCompiler })` + `translate()`, with a probe statement between `onError?.()` and the `return`:

| message shape | dev | production | line after `onError?.()` reached? |
|---|---|---|---|
| `'Hello {name}'` | reaches ICU | reaches ICU | n/a |
| `{type:0, body:…}` (AST) | **throws** `SyntaxError: Message compilation error: [i18n] ICU compiler requires string messages (key: greeting)` | **throws** `Error: [i18n] ICU compiler …` | **no** |
| message function with `.source` | returns `"precompiled"` | returns `"precompiled"` | **no — compiler never called** |

Row 3 is the second half of the finding. `core-base` tests `isMessageFunction` **before** calling any custom compiler — at `translate()` L1534 and again at `compileMessageFormat()` L1675 — so a pre-compiled message function bypasses ICU **silently** and renders with vue-i18n's own pipe-plural semantics. That is the exact "silently mis-render" the comment claims to be preventing, and it is the case the comment names *first*.

**Which shape does `include` actually emit?** `@intlify/unplugin-vue-i18n@11.2.5` `lib/index.mjs` hardcodes `jit: true` at all four resource-transform call sites (L471, L500, L540, L576) — not a user-facing option. Run against `@intlify/bundle-utils@10.0.1` `generateJSON`: `jit: true` → a `{"type":0,…,"body":…}` object (non-string → the guard fires → throws); `jit: false` → `fn.source="Hello {name}"` (a message function → bypassed). So the guard **is** reachable for the documented `include` case, and the gotcha's "AST/JS functions" is half true — with the false half being the one that produces no error message to search for.

### Why it is worth a patch rather than a note

"Fail loudly" and "render the key" are different failures for a user of this skill. A throw out of `t()` inside a Vue render function takes out the component subtree through `app.config.errorHandler`; a key-shaped string is a visible but survivable placeholder. The comment promises the second and the code delivers the first — and the troubleshooting entry at L969 sends a user looking for a rendered placeholder when what they have is an exception.

The patch changes **no emitted runtime behaviour**. It corrects the comment in both copies, keeps `return () => key` (it is reachable on a host that passes no `onError`, and removing it breaks the `MessageCompiler` return type) with an accurate annotation, rewrites the L969 gotcha to say **AST** and to name the thrown shapes per build, and **adds a second gotcha** for the silent function case, which today has no entry at all.
