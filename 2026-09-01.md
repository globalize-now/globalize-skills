## (F) — `@lingui/swc-plugin@^6` is a hard build break on every Next.js

### Why this was the target

Yesterday's run closed the `@swc/core` host-floor question on the Vite stacks by building a ladder, and said in as many words that the same question **"remains open for the Next.js one."** Item 28's rule — *when a claim names a specific version boundary, and the boundary is cheap to cross in a fixture, cross it before the claim leaves this log* — makes that the oldest unverified claim in the log. ### The experiment

A Next.js App Router fixture — `app/layout.js`, `app/page.js` with a `t` macro from `@lingui/core/macro`, `experimental.swcPlugins: [['@lingui/swc-plugin', {}]]` exactly as the skill writes it — built in the cloud container across a Next × plugin matrix. Every rung a clean `rm -rf node_modules package-lock.json` + `npm install`, with **requested and resolved versions printed per row and read as a pair** (item 29).

**Negative control:** the same fixture with `swcPlugins` removed fails with `Module not found: Can't resolve 'babel-plugin-macros'` / `'@babel/types'` — an untransformed `@lingui/core/macro` import reaching the bundler. A clean exit is therefore reachable **only** when the plugin actually ran, which makes exit status a valid signal here, and the three failure modes are separable from it by error string. Without the control, "rc=0" would have meant nothing.

### What this establishes

1. **`@lingui/swc-plugin@6.7.0` runs on no Next.js release.** Its pinned `swc_core@77.1.1` is newer than every plugin runner Next has shipped. `^6` resolves to `6.7.0`, so the skill's own install line is a build break on current Next.js — since **2026-08-27**, when 6.7.0 published.
2. **The Next.js floor is 16.1.0.** `16.0.0` and `16.0.11` reject `6.2.0` and `6.6.0` as well; `16.1.0` and up accept them. Below 16.1.0 *nothing* in the `6.x` line loads.
3. **The file's escape hatch was wrong below that floor.** It said to pin to `6.0.0`-`6.1.0`. On Next 15.5.25 both fail exactly as `6.7.0` does. Pinning back is only a remedy **above** the floor, where it is now the default.
4. **The `5.x` line is unreachable, verified by install rather than by reading:** `@lingui/core@^6` + `@lingui/swc-plugin@5.11.0` → `npm error code ERESOLVE ... Found: @lingui/core@6.6.0`.
5. **The Babel fallback works but was under-specified.** Verified end to end on Next 15.5.25: it fails first on `Cannot find package '@babel/types'` (Next bundles its own Babel and does not expose it), then on `@lingui/core/macro: No Lingui config found`, and **then builds clean**. `@babel/core` was installed and removed again — still passes, so it is not required and is not in the install line. It also silently switches the whole project off SWC (`Disabled SWC as replacement for Babel because of custom Babel configuration ".babelrc"`), which the file did not say.
6. **The same cause prints three different ways** — `failed to invoke plugin` on Next 14/15, `Failed to execute SWC plugin` / `failed to run Wasm plugin transform` / `Failed to deserialize program received from host` on Next 16 with too-new a plugin, and a bare `TurbopackInternalError` **panic** on Next 16.0.x whose real cause is only in the panic log. An agent matching on the string yesterday's runs settled on would have recognised one of the three.

### What it does *not* overturn

The Vite-side conclusion from yesterday is untouched and was re-checked against this: on a host you install, the floor is `@swc/core` ≥ 1.15.0 and the plugin version is irrelevant — `6.7.0` runs fine there. The six Vite-family stacks keep `@lingui/swc-plugin@^6` in the manifest, correctly. **The two answers differ because the two stacks differ in who owns the host**, which is the distinction neither #63 nor #69 had drawn.
