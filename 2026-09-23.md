## The finding: the PO loader drops a key whose dot-path overlaps another

**→ [#88](https://github.com/globalize-now/globalize-skills/pull/88), ready for review.**

### Discharging the queue head first

The head was *"does `@intlify/unplugin-vue-i18n@11.2.5` still parse a PO-backed SFC under `typescript-estree` 8.70.1?"* It carried real weight: 8.70.1 has runtime changes in `convert.js`, and the plugin depends on `@typescript-eslint/typescript-estree@^8.13.0`, which resolves to 8.70.1 on a fresh install today (confirmed — `npm i` put 8.70.1 in the tree).

But the dependency is **never loaded** in anything this skill builds. In 11.2.5 there are exactly two import sites:

- `extractKeysFromScript`, reached only from `treeShakingPlugin`, which is constructed only when `resolvedOptions.treeShaking` is set
- a `vite.config()` hook in `directivePlugin`, constructed only when `optimizeTranslationDirective` is set

`grep -rn 'treeShaking\|optimizeTranslationDirective'` across `skills/` returns **nothing**. The skill configures `runtimeOnly`, `compositionOnly` and `strictMessage` and nothing else. Claim discharged: not "unaffected", but **unreachable**.

Worth recording for later, though it changes nothing today: `extractKeysFromScript` falls back to a **regex** when the `typescript-estree` import or parse throws, and the regex hardcodes `hasDynamic: false`. A project that did enable `treeShaking` with `dynamicKeyStrategy: 'ignore'` would silently delete keys it failed to parse. That is upstream's to own; it is item 21's exact shape and is queued as an upstream watch, not a skill change.

### The defect, next door

The standing order says the neighbours of a claim are part of the claim. The neighbour here is `poLoader`, which the PO path installs. It rehydrates a flat `msgid` list into the nested object vue-i18n resolves against, and `setByPath` resolved an overlap by **overwriting**.

Measured on Vite 7.3.6, vue 3.5.43, vue-i18n 11.4.12, `@intlify/unplugin-vue-i18n` 11.2.5, gettext-parser 8.0.0, Node 22.23.2, with the loader **extracted programmatically from `main`'s markdown**:

| case | result |
|---|---|
| `Cart.items` then `Cart.items.empty` | rc 0, emits `{"Cart":{"items":{"empty":"…"}}}` — `Cart.items` gone |
| `Cart.items.empty` then `Cart.items` | rc 0, emits `{"Cart":{"items":"…"}}` — `Cart.items.empty` gone |
| control `Cart.count` + `Cart.items.empty` | rc 0, **both** present |
| Step 9 PO catalog check on the colliding catalog | **rc 0** |
| `t('Cart.items')` on the emitted catalog | **`"Cart.items"`** |

So the survivor depends on **file order**, which means `msgcat --sort-by-msgid` — recommended by this repo's own § Notes on PO Tooling Round-Trips — or any TMS re-sort can silently change which string ships.

**The stale-checkout trap fired here and was caught.** I first extracted the loader from the mounted working copy, which is 20 commits behind (item 49). `main`'s loader differs: it skips untranslated entries instead of defaulting to the `msgid`. `setByPath` is byte-identical between the two, so the finding survived — but every number in #88 was **re-measured against `main`'s loader** before it was written down. A measurement taken from that checkout is a measurement of a tree nobody ships.

### Why it is reachable

- `po-format.convert.md` § Nested namespaces teaches `Auth.login.title` / `Auth.login.submit`, and `convert.shared.md` permits "max 2 levels of nesting" — a two-segment key beside a three-segment one is ordinary convert output.
- Step 7 seeds the **flat** keys `welcome` and `messages`. Any later `messages.*` key destroys the seed. Measured.
- It also fires through `msgctxt`: `msgctxt "a"` and `msgctxt "a.b"` on one `msgid` mangle to `K__ctx_a` and `K__ctx_a.b`. Measured.
- **JSON cannot express the collision at all**, which makes `convert.shared.md`'s *"the PO loader re-hydrates dot-paths into the same nested shape"* false. That sentence is corrected in #88.

### The fix, and how it was checked

`setByPath` throws on both collision directions and on two entries that mangle to one key. Vite prefixes the plugin name and names the offending `.po`. Fault-injected eight ways standalone (3 controls pass, 5 collisions throw) and four ways through a real `vite build`, with the loader **extracted from the branch**, not retyped. The Step 9 PO check gained the same detection and was run over two-locale fixtures: healthy rc 0, the skill's own 3-level example rc 0, both collision shapes rc 1, and the pre-existing missing-key path still rc 1.

**(G) sweep written from the symptom** — `split('.')`, `setByPath`, deep-merge, `__ctx_`, dot-path rehydration — across `skills/`. `setByPath` exists in exactly **one** file; Quasar says "copy verbatim" and Nuxt imports it, so one edit covers all three variants. The sweep surfaced `next-intl`'s PO path, which runs a **different** loader — handled below, under item 51's rule.

**Deliberately not done**, named in the PR: hard-fail vs. warn is a product call (an existing project with a colliding catalog will now fail to build); and `msgctxt "nav.header"`, which splits across levels but **still resolves**, measured — a shape surprise, not a defect, flagged so it is not re-discovered as one.

**Why a PR and not an issue:** the defect, the fix and the fix's validation were all produced by commands.

## The near-duplicate, and what checking first bought

The (G) sweep reached `next-intl/po-format.setup.md`, whose PO path uses next-intl's own `experimental.messages` loader. Reading `BuiltInPoCodec` in 4.14.6 turned up a migration guard and a comment saying the PO format "now follows the gettext convention: the source text in `msgid` and the message key in `msgctxt`" — while this repo's reference teaches `msgid` **is** the key. That reads like a second finding.

**It is [#67](https://github.com/globalize-now/globalize-skills/pull/67)**, open as a draft since 2 September, which documents exactly this. So the artifact is a measurement, not a PR.

`next-intl@^4` → 4.14.6 → `@eloqnt/format-po@^0.1.0` → **0.1.0**. #67's analysis was written against **0.0.4, a version no `next-intl` release has ever resolved to** (the 2026-09-02 run already caught that and corrected the branch). I fetched 0.1.0's 2 751-byte `dist/index.mjs`, read its mode selector, then **ran `decode`** — one fresh codec per case, because the mode is cached per locale:

| catalog | decoded id |
|---|---|
| skill's seeded header, `msgid "common.title"` | `common.title` |
| + `X-Crowdin-SourceKey: msgstr` | `common.title` |
| + `X-Message-Key: msgctxt` | `common.title` |
| `msgctxt "icon-tooltip"` + `msgid "ItemRow.delete"` | **`icon-tooltip.ItemRow.delete`** |

**#67's § 1 holds at 0.1.0.** The mode selector is unchanged from 0.0.4, so its three-layout table is still correct; the `?? 'key-msgctxt'` fallback is reachable only for a catalog with no header and no messages, which does not affect any conclusion. The plain seeds keep working in **all three** modes, because a key with no `msgctxt` decodes to `msgid` under each of them — which is also why the `msgctxt` defect stays silent.
