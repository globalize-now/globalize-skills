## Finding: `next-intl` pulls the broken SWC addon directly, and `next.config` is where it lands

**→ draft [`25-next-intl-swc-native-binding-troubleshooting.md`](./pending-issues/25-next-intl-swc-native-binding-troubleshooting.md) + [`.patch`](./pending-issues/25-next-intl-swc-native-binding.patch). Unfiled — no token. PR-shaped, ready for review, not draft.**

### The dependency

`next-intl` declares `@swc/core` in `dependencies`, not `peerDependencies`, so it is installed whether or not the project uses SWC itself:

| `next-intl` | declared `@swc/core` range | from |
|---|---|---|
| `4.5.0` | `^1.13.19` | 2025-11-07 |
| `4.5.4` | `^1.15.2` | 2025-11-19 |
| `4.13.7` | `~1.15.47` | 2026-08-17 |
| **`4.14.0`–`4.14.8`** | **`~1.16.0`** | 2026-08-27 |

The `^` → `~` narrowing at 4.13.7 reads as deliberate ABI caution upstream. It is not enough: the published stable 1.16 line is `1.16.0`, `1.16.1`, `1.16.2`, `1.16.12`, so `~1.16.0` picks **`1.16.12`** — and 1.16.3–1.16.11 never existed as stable, which is why a one-minor-wide tilde still spans the repackaging.

### The load path

Both entry points reach it at **module scope**, unconditionally:

| entry | path to `@swc/core` |
|---|---|
| `require('next-intl/plugin')` — `next.config.js` | `dist/cjs/development/plugin.cjs` **line 9**, top of file |
| `import … from 'next-intl/plugin'` — `next.config.ts` / `.mjs` | `plugin/createNextIntlPlugin.js` → `plugin/extractor/initExtractionCompiler.js` → `extractor/ExtractionCompiler.js` → `extractor/extractor/MessageExtractor.js`, static `import {transform} from '@swc/core'` |

The ESM chain was walked by resolving `from '…'` specifiers transitively from `createNextIntlPlugin.js` — 21 files visited, one hit. Neither path is lazy, and neither is behind a config flag.

### Measured

Clean `npm i` into an empty project, twice, same machine:

| `@swc/core` resolved for `next-intl@4.14.8` | `require('@swc/core')` | `require('next-intl/plugin')` | `await import('next-intl/plugin')` |
|---|---|---|---|
| **`1.16.12`** (what `~1.16.0` picks) | **throws** | **throws** | **throws** |
| **`1.16.2`** (`overrides`) | OK | OK | OK |

The throw is `Failed to load native binding` with `cause[1]`:

```
ERR_SWC_NATIVE_CACHE: SWC native addon: validate cache root
/sessions/…/.cache: cache root has a parent writable by another user without
trusted sticky protection. Reinstall the native package if its payload is
damaged; check SWC_NATIVE_BINDING_CACHE and directory permissions for
materialization failures.
```

`cause[0]` is the plain `MODULE_NOT_FOUND` for `./swc.linux-arm64-gnu.node` — i.e. the stub failed to materialize and then the loader fell through to "file missing", which is why the top-level message is so uninformative. Corroborating: the 1.16.12 binding is a **10 650 960**-byte stub, the 1.16.2 one the real **33 313 448**-byte addon; `@swc/wasm` present and unused in the 1.16.12 tree; `@swc/core/index.js` line 66 `var binding_1 = require("./binding")` confirmed byte-present, outside the L76–93 `try/catch` that would use the fallback. `npm` exit 0 both times. This is exactly draft 24's mechanism, reached through a different package.

## The 4.14.8 diff itself, and the close of half an (F) head

Read as a tarball diff, not from release notes. Seven files differ between `4.14.7` and `4.14.8`, and every functional change is one thing: PO references gain an optional `column`, `compareReferences` tie-breaks on it (`… || (refA.column ?? 0) - (refB.column ?? 0)`), and `areSourceMessagesEqual` compares it. `@eloqnt/format-po@0.1.1` is the producer side and its `index.mjs` diff is **a single expression** in the encode-side sort comparator, plus `column?: number` on the type.

**Not actionable, and this closes the `@eloqnt/format-po` half of carried (F) head item 57**, which held "decode-mode changes" as unverified:

1. **`decode` is byte-identical** between `0.1.0` and `0.1.1`. The three-way mode detection (`id-msgid` / `key-msgctxt` / `gettext`) that `po-format.setup.md` documents is untouched. The carried head assumed decode-side movement; there is none.
2. The new sort runs only when the mode is **not** `gettext` (`_ = f === 'gettext' ? s : s.toSorted(g)`), and `po-format.setup.md` records that this reference's scaffold produces plain **gettext** catalogs — so it does not apply to catalogs these skills generate.
3. Columns reach the file only when the existing catalog already carried line numbers (`m = u.get(locale) ? e => e : c`, where `c` collapses references to unique paths). Catalogs written to this reference's conventions are unaffected.

Recorded in draft 25 § "The 4.14.8 diff itself" so a later run does not re-derive it. If anything it reduces diff churn.
