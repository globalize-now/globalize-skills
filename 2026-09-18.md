## The finding — the add-on's headline rule is not in the preset it tells you to extend

**→ [#85](https://github.com/globalize-now/globalize-skills/pull/85), ready for review.**

`eslint-plugin-lingui@0.16.0` adds `require-comment` and `require-directive-reset` plus a `lib/directives.js` helper. `flat/recommended` is byte-identical between 0.15.0 and 0.16.0. Item 35's rule says read each new rule's diagnostic as a bug report about the ecosystem and check whether this repo has that bug:

- **`require-comment`** — *"Tagged template literal doesn't support 'comment'. Use `t({ message, comment })` … instead."* The repo already teaches exactly that (`convert.standard-react.md`, `rules.template.md` — the object form, every time). **No bug.**
- **`require-directive-reset`** — `lingui-set` / `lingui-reset` comment directives are sticky to end of file. Grepped `skills/` and `docs/`: the repo never writes or documents them. **Nothing to act on.**

Both clean. The finding came from the question *underneath* them — which config surface are these rules reachable from — and the answer falsifies a shipped table.

### `no-unlocalized-strings` is not in `recommended`, at any version

Measured two independent ways (item 41): by `require()`ing three separately-installed copies of the plugin and printing `configs['flat/recommended'].rules`, and by asking ESLint itself with `--print-config`. The two agree.

| version | rules in plugin | `flat/recommended` | includes `no-unlocalized-strings` |
|---|---|---|---|
| 0.14.0 | 11 | 5 | **no** |
| 0.15.0 | 12 | 5 | **no** |
| 0.16.0 | 14 | 5 | **no** |

The five, identical at all three: `t-call-in-function` (**error**), `no-single-tag-to-translate`, `no-single-variables-to-translate`, `no-trans-inside-trans`, `no-expression-in-message` (all **warn**).

Add-on 2's table lists `no-unlocalized-strings` first, as *"the most common gap"*, and omits `no-single-variables-to-translate` — **one false row and one missing true one**. It also contradicts a sentence fifteen lines below it, added by #74 on 2026-09-06: *"at both `0.14.0` and `0.15.0` `flat/recommended` enables the same five rules."* The correct fact was already in the file, in the section next door.

### What it costs — three trees

ESLint 9.39.5 + `typescript-eslint` 8 + `eslint-plugin-lingui@0.16.0`; each tree a single-install control or a copy of one with exactly one thing changed (item 29).

| tree | config | `no-unlocalized-strings` violations | exit |
|---|---|---|---|
| **A** | Add-on 2's *Configure* step verbatim — `lingui.configs['flat/recommended']` | **0** | 0 |
| **B** | A + the tuned rule block from the *configuration* section, actually applied | **4** | 1 |
| **C** | A + a file with a real `no-trans-inside-trans` violation | `0 errors, 3 warnings` | **0** |

Tree A's source contains `<h1>Dashboard</h1>`, `<button aria-label="Close the dialog">Save changes</button>` and `<p>You have unpaid invoices</p>`. **Zero problems, exit 0.**

Three things are worse than they look.

1. **The file's framing hides it.** The *`no-unlocalized-strings` configuration* section opens *"This rule is the noisiest by default because it flags every string literal in JSX"* and tells the reader to **tune** it — language that only parses if the rule is already on. A reader who decides tuning is not worth it for a small codebase gets the rule off, and nothing says so.
2. **Tree C is the item-21 half.** Add-on 2's acceptance step is *"report the count of new errors"*. Four of the five preset rules are warnings and ESLint exits 0 on warnings, so a report built from the exit code or `errorCount` reads clean on a file with three real violations.
3. **The convert pipeline inherits it.** `convert.recall-self-check.md` is the *authoritative* recall scan for every Lingui conversion. It runs ESLint, keeps only `ruleId === "lingui/no-unlocalized-strings"` messages, and then: *"If the list is empty, the recall gate passes — set status `succeeded` as usual."* On a project configured as Add-on 2 describes, that filter matches nothing. **The backstop for detection misses passes because the thing it measures never ran.** Item 45's rule, in a second skill, found by following the defect rather than by auditing the file.

### The fix

One gate, fault-injected in both directions before being trusted:

```bash
npx eslint --print-config src/<any-source-file> | grep -q '"lingui/no-unlocalized-strings"'
```

No match in tree A, match (with the tuned options attached) in tree B. It is added to Add-on 2's *After install* step and to the recall self-check, where it carries the rule in words: **an empty list from a scan that never ran is not a pass.** Alongside it: the preset table corrected with severities, an explicit *enable it* section replacing the "configuration" framing, the intro's "missing translator comments" claim corrected (no rule did that before 0.16.0, and `require-comment` still does not unless enabled), the pin `^0.15` → `^0.16`, and the `webext` line that credited the preset with wiring the rule.

**Deliberately not done** (item 20): `require-comment` is **named and not enabled**. Turning it on reports one error per unannotated message across a whole catalog — a policy decision about translator-context coverage, adjacent to [#23](https://github.com/globalize-now/globalize-skills/issues/23), not a setup default. Likewise untouched: whether `no-unlocalized-strings` ships at `error` or `warn`, and whether Add-on 3's CI integration should add `--max-warnings 0`. Both reasonable; neither a library-check call.

**Why a PR and not an issue:** the defect, the fix, and the fix's own validation were all produced by commands. The parts that need a human's judgement are named in the PR and left out of it.
