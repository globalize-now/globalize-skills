### `next-intl` 4.13.3 → 4.13.4 (published 2026-07-23)

Single bugfix: *"Avoid `usePathname()` reads for non-locale-switching links, avoiding unnecessary `<Suspense>` wrappers with partial prefetching"* ([#2362](https://github.com/amannn/next-intl/issues/2362), by @ceolinwill). This is an internal optimization of next-intl's own `<Link>` component — it reduces client work for links that don't switch locale so they no longer force `<Suspense>` boundaries under partial prefetching.

- **`engines`:** absent (unchanged). **peers:** unchanged (`next ^12–^16`, `react ^16.8–^19`). **deps:** only the internal versioned siblings bumped `4.13.3 → 4.13.4` (`use-intl`, `icu-minify`, `next-intl-swc-plugin-extractor`); `negotiator`, `@parcel/watcher`, `@swc/core`, `po-parser`, `@formatjs/intl-localematcher` all identical.
- **`^4` pin admits it.** No install-line or version-note change needed.
- **Not actionable.** The skill's `usePathname` references (`next-intl/code.md`, `nextjs/app-router/next-intl.setup.md`) document the *public API contract* of the locale-aware `createNavigation` wrappers (that `usePathname` returns the path with the locale prefix stripped). 4.13.4 changes only next-intl's internal Link plumbing, not that contract — grep confirms the skill never asserts on Suspense/prefetch behavior. This is the same 4.13.x forward-compat / Next.js-16 prefetch train already tracked under carried open item #9.
