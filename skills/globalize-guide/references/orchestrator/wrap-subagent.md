Read `.agents/globalize-rules.md` **first** — Phase 2 generated it for exactly this project, and it is the authority on which macro to use, how to handle plurals, what to skip, and where catalogs live. Then read these reference files for the mechanics of finding and converting existing strings: {paths from manifest-snapshot.references.convert}. If the two ever disagree on an authoring rule, `.agents/globalize-rules.md` wins — it carries this project's real paths and locales.

For each file: identify translatable strings, wrap with the correct macro, add translator comments inline per the rules in the reference. (Paraglide is key-authored with no macro — instead of wrapping, author a descriptive, context-encoding key plus its catalog entry and replace the string with the `m.key()` call. **On the default PO catalog format**, author the entry into `messages/{baseLocale}.po` as `#.` comment + `msgid "key"` + `msgstr "ICU body"` — `.po` carries `#.` comments, so DO add them, following `references/languages/js-ts/frameworks/sveltekit/paraglide.convert.md`. **On the ICU-JSON catalog format** (`decisions.setup.catalogFormat === "json"`), the inlang/ICU JSON model has no translator-comment field, so do NOT add comments — descriptive key naming is the only disambiguation lever; follow `references/languages/js-ts/libraries/paraglide/json-format.convert.md` instead. **Android is also key-authored, with no macro and no automated extractor** — author a `<string name="key">value</string>` (or `<plurals>`) entry into `res/values/strings.xml`, then replace the literal with `getString(R.string.key)` / `resources.getQuantityString(R.plurals.key, count, count)` in Kotlin/Java, `stringResource(R.string.key)` / `pluralStringResource(...)` in Compose, or `@string/key` in XML layouts. Android XML **supports `<!-- -->` comments**, so DO add a short translator comment above non-obvious keys, plus `<xliff:g>` for do-not-translate runs; follow `references/languages/android/native/android-strings.convert.md`.) **Before marking a file done**, run the per-file checks in the convert reference's *Mechanical self-checks* section where it has one (Lingui: unused imports in the file you touched, then read your diff back for changed display values, index list keys, text re-wrapped inside a `<Trans>` child tag, and inline tags inside `<Trans>` missing `_t`) and fix what they report. Update `.globalize/progress/wrap-N.json` after each file (atomic write). Do NOT run `extract` or `compile` — that runs once after all wrap subagents complete (Android has no extract/compile — the verify worker only validates).

**The format pass** (files tagged `formatting` or `both`): wrapping a string makes it translatable; it does not make a number, price or date render correctly. Phase 2 created this project's formatters module and `.agents/globalize-rules.md` names its real import specifier. Follow `references/languages/js-ts/convert.format-pass.md` for the rewrite table, the never-convert list and the progress fields — or, on Rails / Android / iOS, the **"Convert hand-rolled formatting"** section of the language's own convert reference (`rails.convert.md`, `android-strings.convert.md`, `string-catalog.convert.md`), which carries the same guidance in that language. **Convert formatting AFTER wrapping the strings in the same file**, never before: a formatted value usually ends up as a placeholder inside a wrapped message, so the placeholder-naming rule in `.agents/globalize-rules.md` applies to it, and doing formatting first means naming the placeholder twice. On a `formatting`-only file there is nothing to wrap, so the format pass is the whole job.

**Edit hygiene.** Change only what wrapping and formatting require: no unused imports left behind (remove an import the rewrite made dead, add only the macros you use), no reformatting, re-indenting or reordering of code you did not otherwise touch. A diff reviewer should see i18n changes and nothing else.

Ambiguity protocol and progress schema as in Phase 2 (`setup-subagent.md`; schema in `plan-format.md`).
