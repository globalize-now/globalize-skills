### #62 — the documented fix for an install failure was itself an install failure

Six files in `globalize-guide` (and a seventh elsewhere — see below) told the user, on a build failure, to pin `@lingui/swc-plugin` to an exact old version. Read from the packument this run:

- `5.8.0` → `peerDependencies: {"@lingui/core": "5"}`, and `peerDependenciesMeta` lists only `next` and `@swc/core` — so `@lingui/core` is a **required** peer, against stacks installing `@lingui/core@^6`. `ERESOLVE`.
- `4.0.8` → required peer `@lingui/macro@4`, a package the Next.js stack does not install in any version.

And the premise is four majors stale: SWC's Wasm plugin ABI has been backward-compatible since **`@swc/core` 1.15.0** (rkyv → cbor, `Unknown` enum variants), and `@lingui/swc-plugin@6.2.0+` builds against `swc_core@66.0.3` under it. Pinning backwards moves the user *out* of the compatible regime — `5.8.0` is built at `swc_core@45.0.2`, below the `>= 47` threshold the scheme needs.

Each note is now an ordered ladder: raise the host → only then `plugins.swc.rs` with a peer-satisfiable pin (`6.0.0`–`6.1.0` for a v6 project, never 5.x/4.x) → otherwise the Babel variant. Ready for review: every claim is a metadata lookup or a quoted upstream sentence. **Closes item 3.**

### #63 — the host floor, split out because it carries a judgement call

`vite-swc-lingui` installs `@lingui/swc-plugin@^6` and **no SWC host**, alone among the five Lingui-SWC stacks. `@vitejs/plugin-react-swc` only crosses into the 1.15 line at **4.2.3** (`@swc/core@^1.15.11`; 3.11.0 is `^1.12.11`, 3.8.1 is `^1.11.11`), so a project on 3.x runs the plugin against a pre-cbor host.

The fix — add `@vitejs/plugin-react-swc@^4` to the stack's dev packages — matches the four siblings exactly, but on *this* stack it upgrades a build plugin the project is already using. That is a real consequence, so it went out as a **draft** with three questions under `## Needs a human` rather than as a confident change. Splitting it kept #62 shippable.
