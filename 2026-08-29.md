## next-intl 4.14.1 → #67, commit `6ffdad5`

[4.14.1](https://github.com/amannn/next-intl/releases/tag/v4.14.1) (2026-08-28T09:34:57Z) has one line of release notes — *"Unbreak `experimental.messages` without a `messages.sourceLocale`"* — and the whole `v4.14.0...v4.14.1` diff outside changelogs and version bumps is **+29/−6 in one file**, `packages/next-intl/src/plugin/getNextConfig.tsx`.

It fixes a regression **4.14.0 introduced**. Diffing `getNextConfig.tsx` at `v4.13.7` against `v4.14.0`, the only change in the file is:

```diff
   function getCatalogLoaderConfig() {
-    const messages = pluginConfig.experimental!.messages!;
+    const experimental = pluginConfig.experimental!;
+    const messages = experimental.messages!;
+    const sourceLocale = (messages.sourceLocale ??
+      (typeof experimental.extract === 'object'
+        ? experimental.extract.sourceLocale
+        : undefined))!;
     ...
-          })
+          }),
+          sourceLocale
```

`sourceLocale` is spread in unconditionally, so with `experimental.messages` set and no `extract` block it lands as `undefined`. Next.js validates Turbopack loader options by `isDeepStrictEqual(options, JSON.parse(JSON.stringify(options)))`, and `JSON.stringify` drops undefined-valued keys, so the check can never pass ([#2394](https://github.com/amannn/next-intl/issues/2394), which quotes the error and diagnoses it precisely). `precompile`, three lines above, was already spread conditionally for exactly this reason.

### Why it is actionable here

**The scaffold in `po-format.setup.md` does not set `sourceLocale`.** It is the shape that breaks. The user-visible failure names neither next-intl nor the option:

```
Error: loader next-intl/extractor/catalogLoader for match "*.po" does not have serializable options.
Ensure that options passed are plain JavaScript objects and values.
```

Two things read out of `getNextConfig.tsx@v4.14.0` rather than inferred:

- **Dropping `--turbopack` is not a way around it.** `shouldConfigureTurbo = useTurbo || isNextJs16OrHigher()`, and the catalog branch throws `Message catalog loading requires Next.js 16 or higher.` — so any project that can use this path at all is on Next 16, where the turbo rules are registered whether or not the flag is passed. § Pre-flight offers "drop `--turbopack`" as remedy 1 for the *unrelated* CJS problem, and someone could reasonably reach for it here.

## The correction to yesterday — #67, commit `2bfbc0a`

Re-verifying yesterday's PO conclusions against the version that actually ships turned up **two errors in this task's own output**, one of which changes what the reference tells a user.

### 1. The evidence was read one patch too new

next-intl 4.14.x depends on **`@eloqnt/format-po@^0.0.3`**. npm's caret on a `0.0.x` range means `>=0.0.3 <0.0.4` — **exactly `0.0.3`**. `latest` is `0.0.5`. Yesterday's layout table was established by deminifying **`0.0.4`**'s `dist/index.mjs`, a version that never enters the tree.

Both tarballs unpacked and diffed this run. **The conclusion survives:** `0.0.4`'s only change is encode-side — one extra per-locale map recording whether parsed references carried line numbers, so reference style is preserved on write, matching its changelog. `decode` and the layout detector are behaviourally identical: same three-way `X-Crowdin-SourceKey` / `X-Message-Key` / gettext split, same `id = layout === 'key-msgctxt' ? (msgctxt ?? msgid) : (msgctxt ? [msgctxt, msgid].join('.') : msgid)`. Right answer, wrong evidence. → **item 26.**

### 2. The throw is in next-intl, and it is a substring match

Yesterday's table — and #67's, copied from it — put *"throws, with a migration link"* in the `@eloqnt/format-po` row. **`@eloqnt/format-po` never throws in `decode`.** Its only `throw` is `Missing source message for id …`, on the encode path. The guard is in next-intl's wrapper, `BuiltInPoCodec.tsx`:

```ts
function assertMigrated(content: string) {
  if (content.includes('X-Crowdin-SourceKey: msgstr')) {
    throw new Error('This catalog uses the previous PO layout of next-intl, …');
  }
}
```

`content.includes` on the **raw file text**, that exact spelling, one space — not a parsed header lookup. `X-Crowdin-SourceKey:msgstr` with no space passes the guard, and is then decoded by the **gettext** branch, keying on `msgctxt` + `.` + `msgid`. On a previous-layout catalog that yields wrong keys and `MISSING_MESSAGE` at render, **with no build error**.

This matters more than a citation fix. The entire point of #67's `msgctxt` half is the distinction between a loud failure and a silent one, and this section had put a silent failure on the loud side. The reference's `grep -l "X-Crowdin-SourceKey"` was already looser than the guard, so it catches the near-miss spellings; what changed is the prose, which now says to treat any hit as *"migrate"* rather than *"the build will tell me"*. The same wrapper comment confirms a custom codec importing the package directly opts out of the guard — which is what makes #67's remedy 2 work, so that is now stated rather than assumed.
