## (F) — open item 16 settled, and it moves the floor

It is no longer undetermined. Three things came out of reading `swc_plugin_runner` at the tag `@swc/core@1.16.1` is built from, and each is a defect in guidance this repo has already merged.

### 1. The ABI announcement is one-directional, and it was cited for the other direction

Six files carry a near-identical paragraph opening *"SWC's Wasm plugin ABI has been backward-compatible since `@swc/core` 1.15.0"*, cited to [the announcement](https://blog.swc.rs/2025-11-4-wasm-backward-compatibility), and read as reassurance that the host version is a soft concern. The announcement is explicit that it makes an **older plugin work on a newer host** — *"a Wasm plugin compiled against v1.15.0 will now work seamlessly with future versions of SWC."* These stacks are in the opposite case: `@lingui/swc-plugin@^6` resolves to the newest plugin, running on whatever host the project holds.

**Nothing gates that direction.** The runner's only ordered version test is `is_transform_schema_compatible()`:

```rust
if host_schema_version >= self.plugin_core_diag.ast_schema_version {
    Ok(())
} else {
    anyhow::bail!("Plugin's AST schema version is not compatible with host's. Host: {}, Plugin: {}", ...)
}
```

with a `// TODO: this is incomplete` on the line above the comparison. And `PLUGIN_TRANSFORM_AST_SCHEMA_VERSION` is **hardcoded to `1`** under `plugin_transform_schema_v1`; the only other value is `u32::MAX - 1`, behind `plugin_transform_schema_vtest` and commented *"Reserved for the testing purpose."* So the comparison is `1 >= 1` for **every real host/plugin pair, in both directions**. The gate is inert. It is not what catches a mismatch, and a reader who assumes an ordered version check protects them is wrong in both directions.

What catches a mismatch is the AST crossing the Wasm boundary as a serialized struct and failing inside `run()`, surfacing through the `with_context` wrapper — *"failed to run Wasm plugin transform. Please ensure the version of `swc_core` used by the plugin is compatible with the host runtime."*

### 2. `swc_core version mismatch` is not a string SWC emits

Four files tell the agent to look for it. Matched against the **shipped** `@swc/core@1.16.1` native binary (`swc.linux-x64-gnu.node`, 32 MB, from `@swc/core-linux-x64-gnu`):

| String | Present? |
|---|---|
| `failed to run Wasm plugin transform` | **yes** |
| `Plugin's AST schema version is not compatible` | **yes** |
| `failed to invoke plugin` | **yes** |
| `swc_core version mismatch` | **no** |

The guidance sends a user hunting for a string the host cannot print. This is the same class as item 25's substring-guard finding, one level down: *read how the failure actually surfaces before telling someone what to look for.*

### 3. The floor is a `swc_ecma_ast` match, and `swc_core` numbers never match

`@lingui/swc-plugin@6.7.0` embeds `swc_core@77.1.1` (git `7a29dc7`); `@swc/core@1.16.1` ships `swc_core@77.0.2`. **They are not equal and never will be** — the plugin builds against a crates.io release cut between swc tags. An agent told to "match `swc_core`" (remix and webext said *exactly*) cannot follow the instruction, and one that checks for equality concludes a working pair is broken.

What lines up is `swc_ecma_ast`, whose types cross the boundary. Read out of the published `.wasm` binaries and out of `crates/*/Cargo.toml` per tag — not from the upstream compatibility table, which gives only `swc_core`:

| `@lingui/swc-plugin` | `swc_core` | `swc_ecma_ast` |
|---|---|---|
| `6.0.0` / `6.1.0` | `50.2.3` | `19.0.0` |
| `6.2.0` – `6.6.0` | `66.0.3` | `23.0.1` |
| **`6.7.0`** | **`77.1.1`** | **`29.0.0`** |

| `@swc/core` | `swc_core` | `swc_ecma_ast` |
|---|---|---|
| `1.15.46` | `74.0.1` | `26.0.0` |
| `1.15.47` | `75.0.0` | `27.0.0` |
| **`1.16.0`** | `77.0.0` | **`29.0.0`** |
| `1.16.1` | `77.0.2` | `29.0.0` |

So the floor is **`@swc/core` ≥ 1.16.0**, not "the 1.15 line", and — the operational half — **`@vitejs/plugin-react-swc@4.3.3` depends on `@swc/core@^1.15.46`, a range whose own floor is `swc_ecma_ast@26.0.0` and cannot run the plugin.** No `@vitejs/plugin-react-swc` version is a sufficient proxy, including the newest. A fresh install resolves to `1.16.1` and works; **a lockfile written between `1.15.46` (2026-07-19) and `1.16.0` (2026-08-14) does not.** Every corrected copy now says to check `npm ls @swc/core`.

The `@swc/core` bump `~1.15.47` → `~1.16.0` that next-intl made in 4.14.0 — noted yesterday as "corroborating but not bearing on the Lingui host floor" — now reads as the same boundary seen from the other side.
