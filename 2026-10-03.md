### And the obvious fix is the worse one

`ng add @angular/localize` with no version looks correct, because the CLI has a compatible-version search. From the published `@angular/cli@22.2.1`, `src/commands/add/cli.js` **L192**:

|---|---|---|---|
| `@angular/localize` | `range` | `"*"` | **ENABLED** |
| `@angular/localize@^22` | `range` | `"^22"` | disabled |
| `@angular/localize@22.0.0` | `version` | `"22.0.0"` | disabled |

### What the patch does

```bash
npx ng add "@angular/localize@$(node -p 'require("@angular/compiler/package.json").version')" --skip-confirmation --use-at-runtime --project <project>
```

Pins the installed **`@angular/compiler`** version — the package the peer is declared against, present as a plain dependency in both of #91's own Angular fixtures. Run end to end: on a 22.0.0 project, `node -p` → `22.0.0`, install → `@angular/localize 22.0.0`. Quoting verified under `bash` and `dash`; the construct is POSIX and carries no `^`, so the zsh `EXTENDED_GLOB` hazard that `SKILL.md` §2.0's single-quote rule exists for does not apply (zsh is not installed in this sandbox, so that half is reasoned from the absence of `^`, not executed, and the patch says so at the site).

Also in the patch, because the change makes them wrong: *Already applied* tightened from "same major as `@angular/core`" to "same **version** as `@angular/compiler`" (under the old wording a matching major with a stale patch reports already-applied and the converter then runs on a mismatched tools package), and §1.2's detection-table clause "the setup's `ng add` pin read it" corrected, since it no longer does.

**Out of scope on purpose:** a `coreVersion` detection field (the maintainer's call, stated in the draft — the patch reads `node_modules` at install time instead, which also covers the no-lockfile case where a patch number would be a guess), and the Step-2 table row at L27 that labels the step `` `ng add @angular/localize` `` — a label, not a command, left alone to keep the diff tight and flagged in the draft.
