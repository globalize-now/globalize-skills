### The watch itself is still good news

`herb` is tracked for exactly one reason. `setup.add-ons.md` L205–211 and `rails.convert.md` L91 tell the reader that Herb ships **no** hardcoded-string/i18n rule, recommend `erb_lint` + `rubocop-i18n` instead, and say to watch for a Herb i18n rule landing. Two releases went by unread, so the watch was re-run properly — against the code, per trigger (E):

- **v0.10.2** (2026-07-13) — six new rules, every one `a11y-*`: `a11y-no-redundant-image-alt`, `a11y-disabled-attribute`, `a11y-avoid-generic-link-text`, `a11y-svg-has-accessible-text`, `a11y-no-aria-label-misuse`, `a11y-nested-interactive-elements`.
- **v0.10.3** (2026-08-01) — two: `erb-no-commented-out-output-tags`, plus `html-no-space-in-tag` re-enabled. The rest is parser, formatter and CLI work (`--only`, `--all-rules`).

And not trusting the notes either: the rule directory `javascript/packages/linter/src/rules` **at tag `v0.10.3`** holds **107 entries**, and the only name matching `i18n|hardcode|locale|translat|string` is `string-utils.ts` — a shared helper, not a rule. **The skill's claim is accurate at 0.10.3.** Nothing to change; the "as of June 2026" hedge could be re-stamped to name the version it was last verified against, which is cosmetic and listed as an acceptance checkbox on the draft rather than done unilaterally.

Had either release contained the rule, this check would have missed the single event it watches that gem for, and reported clean while doing it.

### Why the gem half fails where the npm half does not

`curl` cannot reach `rubygems.org` from this sandbox — `curl: (56) Received HTTP code 403 from proxy after CONNECT`, reproduced this run from **both** the device shell and the cloud container, while `registry.npmjs.org`, `api.github.com` and `raw.githubusercontent.com` all answer normally. The gem half therefore runs through `web_fetch`, which returns *a small model's prose summary of the JSON*, not the JSON.

That is the whole asymmetry: **npm is diffed field-by-field in code; gems are diffed by reading a sentence.** Of the five, `herb` is by a wide margin the largest and most repetitive document — 449 published versions, eight platform variants per release, so the newest rows differ only in `platform` — the exact shape that invites a summariser to collapse rows or answer from the wrong one. That is a plausible mechanism, not a proven one, and the part that *cannot* be recovered is which run first got it wrong: only the summaries were ever kept, and `library-checks/` is gitignored, so there is no history to diff. Recorded as unknown rather than guessed.

The fix in the draft is structural, not "be careful": read two endpoints per gem, ask for literal strings and compare them in code, never report a gem unchanged without a date read that run, print the raw values in the report. The real fix is transport — allowlist `rubygems.org` at the proxy and the gem half becomes as boring as the npm half.

**Trigger (H), adopted this run — asymmetric evidence quality.** (D) is the wrong pattern, (E) the wrong source domain, (G) an incomplete candidate set. (H) is *right pattern, right source, weaker instrument*: when one half of a check runs on structured data and the other on a summary, the second half will eventually produce a confident false negative, and — because both halves print the same sentence — the report will not show which half you are reading. Name the instrument next to the claim.
