## The correction: item 15's ABI claim is withdrawn

Yesterday's report closed its item 15 with an unusual and, in hindsight, load-bearing sentence:

> **What I did not verify, deliberately:** whether swc_core's plugin ABI actually broke between the 1.15 and 1.16 lines. … Someone should check <https://plugins.swc.rs> for the 6.6.0 / 1.16.x pair before treating this as a live break. … I would rather hand over a sharp question than a confident guess.

The question was sharp and the answer is no. Three sources, in increasing specificity:

1. **[SWC blog, 2025-11-04](https://blog.swc.rs/2025-11-4-wasm-backward-compatibility):** *"Starting from `@swc/core` v1.15.0, our Wasm plugins are now backward-compatible! … A Wasm plugin compiled against v1.15.0 will now work seamlessly with future versions of SWC."*
2. **[SWC compatibility docs](https://swc.rs/docs/plugin/ecmascript/compatibility):** the mechanism. The **rkyv** serialization scheme — which required host and plugin to agree on the exact AST memory layout, and is the entire reason plugin/runtime pairs had to be locked — was replaced with **cbor**, which is self-describing and records field layout as metadata in the byte array. Every AST enum also gained an `Unknown` variant so a plugin can round-trip nodes it doesn't recognize. Requires the plugin to build with `swc_core >= 47` and `--cfg=swc_ast_unknown`.
3. **[Lingui's compatibility table](https://github.com/lingui/swc-plugin/tree/main/packages/lingui-macro#compatibility):** `@lingui/swc-plugin` `5.10.1` ~ `6.1.0` build with `swc_core@50.2.3` + `swc_ast_unknown`; **`6.2.0` ~ `*` build with `swc_core@66.0.3`.** Both far past 47.

So `@lingui/swc-plugin@6.6.0` (built at `swc_core@66.0.3`) on a `@swc/core@1.16.1` host is the *forward* direction — precisely what the guarantee covers. The 1.15 → 1.16 bump that yesterday's report treated as a live hazard breaks nothing.

### Why the draft got it wrong

Not carelessness with the registry — **the registry cannot answer the question at all.**

| | What it is | Value for `@lingui/swc-plugin@6.6.0` |
|---|---|---|
| `@swc/core` | the **npm** wrapper around precompiled Rust binaries; here, the plugin's test host | `^1.15.33`, in `devDependencies` |
| `swc_core` | the **Rust crate** the Wasm is actually compiled against — the thing that defines the ABI | `66.0.3`, published nowhere in npm metadata |

The two version lines are unrelated (`swc_core@66.0.3` ↔ `@swc/core@~1.15.33`), so the inference "devDep says 1.15, host resolves 1.16, therefore mismatch" was not a near miss. The right source was a Rust crate version documented only in the plugin's README and on `plugins.swc.rs`.

**Method note adopted — trigger (E), source-domain fit.** Before asserting a compatibility constraint, name the artifact the constraint actually lives in. If it is a Rust crate ABI, a Wasm build flag, or a bundled binary, npm metadata is the *wrong domain* and no amount of care with packuments will produce the right answer. This is the second method rule in three days that turns on evidence type rather than evidence quality — trigger (D) was "a zero-hit grep proves nothing if the pattern is wrong notation"; (E) is "a packument proves nothing if the constraint isn't in the packument."

Residual risk, stated because it is not zero: SWC's own docs say the cbor scheme "does not resolve all compatibility issues, such as those caused by field deletions or changes in field types," and Lingui's [issue #179](https://github.com/lingui/swc-plugin/issues/179) notes they have not yet tested it against a release that actually changed the AST layout. Watch item, not a break.

## Finding 2 (certain, medium) — the premise of all six notes is four majors out of date

Each of the six says some form of:

> `@lingui/swc-plugin` must match the `swc_core` version shipped by `@vitejs/plugin-react-swc`.

True through `@lingui/swc-plugin@5.10.0` / `@swc/core@1.14.x`. Since cbor it is no longer the rule — and worse, the advice it generates (*pin the plugin backwards*) moves the user **out** of the compatible-by-construction regime into the brittle one. `5.8.0` builds with `swc_core@45.0.2`, **below the 47 threshold**, so it genuinely is version-locked in the way the note describes. `^6` is not. The note's own recommendation is the only thing that makes its premise true.

The `plugins.swc.rs` lookup should stay as the fallback for genuinely old runtimes — a Next.js shipping a pre-1.15 `swc_core`, or an unupgradable pinned `@swc/core`. It should not be the first instruction.

## Finding 3 (new item 16, medium) — no host floor, and the stack that needs it doesn't install a host

Backward compatibility is **forward-only**. A plugin built at `swc_core@66.0.3` needs a host at `swc_core >= 66.0.3` — roughly **`@swc/core >= 1.15.33`**. Below that the original layout mismatch is still live. So the constraint didn't disappear; it inverted, from a *pair* to a *floor*, and the repo gates neither.
