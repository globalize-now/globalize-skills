## next-intl 4.14.0 → PR #67

[Release v4.14.0](https://github.com/amannn/next-intl/releases/tag/v4.14.0) reads as *"`useExtracted` improvements"*. The substance is [#2393](https://github.com/amannn/next-intl/pull/2393) (merged 2026-08-27T09:14:48Z, 27 files), and the release title understates it: the built-in PO codec was **replaced**, not amended. `src/extractor/format/index.tsx` now resolves `format: 'po'` to a new `BuiltInPoCodec` wrapping the newly published `@eloqnt/format-po`; `POCodec.tsx` and `JSONCodec.tsx` were deleted; `package.json` swapped `po-parser` for `@eloqnt/config`, `@eloqnt/format-po`, `@eloqnt/format-json`.

`@eloqnt/format-po@0.0.4`'s `decode` picks a layout from a header in the catalog:

| Header in the `msgid ""` block | Layout | Key | On 4.14 |
|---|---|---|---|
| `X-Crowdin-SourceKey: msgstr` | previous next-intl layout | `msgid` | **throws**, with a migration link |
| `X-Message-Key: msgctxt` | current extractor layout | `msgctxt` | reads normally |
| neither | plain gettext | `msgctxt` + `.` + `msgid`, else `msgid` | reads normally |

### The load-bearing negative, stated rather than implied

**Catalogs authored the way this repo's scaffold describes are unaffected.** The seed writes only `Content-Type` and `Language`, so decode falls to the gettext branch, whose derivation (`id = msgctxt ? msgctxt + '.' + msgid : msgid`, `message = msgstr`) is byte-for-byte 4.13's. Established by reading `@eloqnt/format-po@0.0.4`'s published `dist/index.mjs` against the deleted `POCodec.tsx` at `v4.13.7` — not inferred from the release note, and not assumed from the fact that the guard exists.

What *does* fail is any catalog next-intl's own extractor wrote on 4.5–4.13: `POCodec`'s `DEFAULT_METADATA` contained `'X-Crowdin-SourceKey': 'msgstr'`, so every one of them trips the guard. The repo said nothing about this, and `grep -l "X-Crowdin-SourceKey" messages/*.po` is a one-line pre-flight, so #67 adds one.

### The bigger finding, which is not a 4.14.0 regression

Chasing the layout question surfaced a defect that was **already there**. Three references teach `msgctxt` as translator context for disambiguating identical source strings. next-intl has never read it that way — both codecs fold it into the key:

```js
// 4.13.7 POCodec.tsx (deleted)            id: msgctxt ? [msgctxt, msgid].join('.') : msgid
// 4.14.0 @eloqnt/format-po, gettext       d = n ? [n, o].join('.') : o        // n = msgctxt, o = msgid
```

The example this repo shipped in `po-format.convert.md` —

```po
msgctxt "icon-tooltip"
msgid "ItemRow.delete"
```

— registers the key `icon-tooltip.ItemRow.delete`, while the call site the *same file* prescribes (`useTranslations('ItemRow')` + `t('delete')`) looks up `ItemRow.delete`. `MISSING_MESSAGE` at render; **nothing fails at build time**. `rules.template.md` carries the same instruction, and that file is on the passive-rule track — it renders into `.agents/globalize-rules.md` in the user's repo, so the bad rule is standing context in every future session on a next-intl PO project. Same severity argument as open item 0.

Also new and undocumented here: **`messages.sourceLocale`**, threaded through `getNextConfig` into the catalog loader, which makes an empty `msgstr` in the source catalog fall back to `msgid`. Added to the option notes.

**[PR #67](https://github.com/globalize-now/globalize-skills/pull/67), draft** — 3 files, +38/−8. Draft because four things are open, listed under `## Needs a human` on the PR: `POCodecLegacy` is a fixture in next-intl's tree rather than a published module, `sourceLocale` is described but not substituted into the config snippets, the migration is described rather than automated, and nothing was executed against a real Next.js build.

The JSON path is untouched. `@eloqnt/format-json` replaced `JSONCodec` in the same release, but its behaviour changes (`null` no longer crashes extraction, booleans/numbers preserved, literal dots not re-nested) all repair cases this repo's JSON scaffold does not produce.
