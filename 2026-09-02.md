## The finding — `next-intl@^4` is a build break on the PO scaffold as of 2026-09-01

### What the release actually is

[`v4.14.1...v4.14.2`](https://github.com/amannn/next-intl/compare/v4.14.1...v4.14.2) is two commits and eleven files, of which nine are changelogs and version stamps. The substance is [#2398](https://github.com/amannn/next-intl/pull/2398): three dependency ranges in `packages/next-intl/package.json`.

```diff
-"@eloqnt/config": "^0.0.2",   +"@eloqnt/config": "^0.1.0",
-"@eloqnt/format-json": "^0.0.3",   +"@eloqnt/format-json": "^0.1.0",
-"@eloqnt/format-po": "^0.0.3",   +"@eloqnt/format-po": "^0.1.0",
```

`next-intl`'s own `dist.unpackedSize` is **408 155 bytes in both releases** — identical to the byte. `peerDependencies`, `peerDependenciesMeta`, `engines`, `exports`, `types`, `main`, `module`, `sideEffects` and `files` are all byte-identical. There is no next-intl code change to read.

Upstream's stated reason is a licensing repair: at `0.0.x` a caret is an exact pin, so consumers were frozen on `@eloqnt/*` versions published **without a license grant** and no package manager could resolve upward into the MIT-licensed ones. Promoting the packages to `0.1.0` makes `^0.1.0` behave like a real caret.

### Why that is a break here

The freeze had a second effect upstream did not have to mention. `0.0.4`, `0.0.5` and `0.0.6` of `@eloqnt/format-po` were **never reachable from any next-intl release**; `4.14.2` delivers all three at once.

| `@eloqnt/format-po` | published | `dist/index.mjs` | reachable from |
|---|---|---|---|
| 0.0.3 | 2026-08-27T07:52Z | 2 253 B | **4.14.0, 4.14.1** |
| 0.0.4 | 2026-08-27T11:35Z | 2 388 B | *nothing* |
| 0.0.5 | 2026-08-28T09:37Z | 2 751 B | *nothing* |
| 0.0.6 | 2026-08-31T11:49Z | 2 751 B | *nothing* |
| 0.1.0 | 2026-09-01T09:02Z | 2 751 B | **4.14.2** |

`0.0.5` is the one that matters: *"Throw a clear error when a PO file contains an empty `msgstr` but no source locale is known, instead of decoding the entry to an empty message."* In the shipped diff the guard clause is **dropped**, not narrowed:

```diff
- f = c !== `id-msgid` && s === `` && r.locale === r.sourceLocale;
+ f = c !== `id-msgid` && s === ``;
+ if (f && !r.sourceLocale) throw Error(`Found an empty msgstr in the "${r.locale}" messages file, ...`);
```

So on `0.1.0` the throw fires for an empty `msgstr` in **any** catalog, not just the source one — and the skill's `po-format.setup.md` sets no `sourceLocale` in any of its three `experimental.messages` snippets.

Three things the matrix establishes that reading could not:

1. **The 4.13.7 rung is why the fix is unconditional.** `sourceLocale` predates the codec swap and is accepted there, so the scaffold needs no version gate.
2. **The 4.14.0 rung collapses two remedies into one.** #67 documents 4.14.0's `does not have serializable options` failure and prescribes *upgrading away from it*. Setting `sourceLocale` clears it too — verified both directions on the same tree.
3. **The source-catalog fallback is not the win it sounds like.** With `sourceLocale` set, an empty `msgstr` in the source catalog falls back to that entry's `msgid` — and because this repo authors `msgid` as a dot-path key, that ships the literal string `common.subtitle` to the page. Documented as a bug to fix, not presented as a fix.

The trigger is any entry with `msgstr ""`, which is the normal state of a project between extraction and translation, and what this repo's own convert flow produces. **Nothing in a user's project has to change**: `next-intl@^4` resolves to `4.14.2` on any fresh install from 2026-09-01 onward.
