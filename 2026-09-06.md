## The finding — this repo teaches the fix for `{0}` and not for `<0>`

### How the run got here

`eslint-plugin-lingui@0.15.0` is the kind of release that is usually a footnote: one new rule, eleven rule files byte-identical, `flat/recommended` unchanged at both versions. Trigger **(B)** says read the diff anyway. The new rule is `no-unnamed-tag-placeholders`, and its message names the problem it exists for — *"must have an explicit placeholder attribute or be configured in `jsxPlaceholderDefaults` to avoid numbered placeholders."* That problem turned out to be live in this repo, independently of the plugin.

### What the skill already says, and what it leaves out

`libraries/lingui/rules.template.md` has a **Naming placeholders** section for *value* interpolation, whose stated rationale is that a positional `{0}` *"tells the translator nothing"*, with `ph()` as the fix. It says nothing, anywhere, about **tag** placeholders. Grepped: `jsxPlaceholder`, `<0>`, `_t=` and "tag placeholder" have **zero hits** across all of `skills/` at `origin/main`.

### What actually happens — extracted, not read

`@lingui/cli@6.6.0` + `@lingui/format-po@6.6.0`, five fixtures, each one `lingui extract`ed and the resulting `.po` read.

```
<Trans>Read the <a href="/tos">terms</a> and the <a href="/privacy">policy</a>.</Trans>
→ msgid "Read the <0>terms</0> and the <1>policy</1>."
```

| Fixture | observed |
|---|---|
| translate `fr.po`, then wrap the first `<a>` in a `<span>` | `<1>` → `<2>`; msgid changes; the completed French entry is rewritten as `#~ msgid` / `#~ msgstr` — **the translation is discarded by a CSS change** |
| `<Trans><a href="/upgrade">Upgrade</a></Trans>` in one file, `<Trans><button>Upgrade</button></Trans>` in another | both extract as `<0>Upgrade</0>`. Catalog **Total count: 1**. One translation, rendered into a link in one place and a button in another |
| same two, with `jsxPlaceholderDefaults: { a: 'link', button: 'button' }` | two entries — `<link>Upgrade</link>` and `<button>Upgrade</button>` |
| two `<a>` in one message under those same defaults | `lingui extract` **fails**, exit 1: `Multiple distinct JSX elements with the same placeholder name (\`link\`)` |
| the same two `<a>` with `_t="a-link"` / `_t="b-link"` | exit 0, `See <a-link>A</a-link> or <b-link>B</b-link>.` |

Three things the fixtures establish that reading the rule's source could not:

1. **The churn case destroys finished work and nothing warns.** `lingui extract` exits 0 and prints its usual table; the loss is a `#~` comment in a file nobody re-reads.
2. **The collision case is worse than the churn case and is invisible at every layer.** Two structurally different call sites, one catalog entry, no diagnostic anywhere — the catalog just says `1`.
3. **`jsxPlaceholderDefaults` is not the safe default it looks like.** It names tags without touching JSX, which is exactly why it is tempting; and it turns any message containing two links into a **build failure**. That is why #74 recommends per-element `_t` and documents defaults with the edge, rather than the other way round.

### Why the fix had to reach `lingui.config.ts`

Running `@lingui/babel-plugin-lingui-macro@6.6.0` over `<a _t="tos" href="/tos">` with **no** `macro` block in the config:

```js
message: "Read the <0>terms</0>.",
components: { 0: <a _t="tos" href="/tos" /> }
```

The placeholder stays numbered **and** `_t` is emitted onto the element, so it reaches the DOM as an invalid attribute. Teaching `_t` in the coding rules without shipping `macro.jsxPlaceholderAttribute` would have produced precisely that — item 25's shape (a guard that looks applied and silently is not), authored deliberately. With the setting, the emitted `components` map is `{ tos: <a href="/tos" />, privacy: <a href="/privacy" /> }` and `grep -c '_t='` on the output is **0**.

Only **four** references in the repo ship a `lingui.config.ts` block; the other seven Lingui variants build the config in `create_config` with nothing to copy. So the setting went into `libraries/lingui/setup.locale-module.md` §5 — the shared "point the framework file at it" contract every Lingui variant reads first — as well as into the four concrete blocks.

### What `lovable-i18n` cost

A `defineConfig`-shaped sweep found four config blocks. A multi-line `<Trans>`-with-inline-tag sweep across all of `skills/` found a fifth, in **`skills/lovable-i18n/SKILL.md`** — a separate top-level skill that sets up Lingui with its own `lingui.config.ts` (object form, `LinguiConfig` type, no `defineConfig`) and its own inline copy of the coding rules. Both greps that missed it were reasonable; the one that caught it was the one written from the *symptom* rather than from the fix's shape. Item 20, and the second sweep is the only reason #74 is not a half-fix.
