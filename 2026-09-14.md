## The finding — a Verify step that passes on an empty catalog

**→ [#81](https://github.com/globalize-now/globalize-skills/pull/81), ready for review.**

The paraglide bump was supposed to be a boundary build and nothing more. Setting up the fixture is what produced the finding: the first `project.inlang/settings.json` used a wrong plugin key, and paraglide **did not complain**.

```
i [paraglide-js] Compiling inlang project ...
✔ [paraglide-js] Successfully compiled inlang project.      exit 0
```

It wrote `messages.js`, `runtime.js`, `registry.js`, `server.js` and `messages/_index.js`. Everything except the per-message modules. `import * as m` gave an object with **zero** keys.

`sveltekit/paraglide.setup.md` Verify step 1 says, verbatim: *"It should complete and emit `messages.js` / `runtime.js` under `src/lib/paraglide/`."* **Both halves pass on a catalog with nothing in it.** Step 1 is the standalone sanity run — the one a script or CI job encodes — and it cannot distinguish a working setup from one with no translations at all.

| settings | compile output | exit | `messages.js`+`runtime.js` | message modules |
|---|---|---|---|---|
| control — `plugin.globalizeNow.po`, correct `pathPattern` | `✔ Successfully compiled` | 0 | yes | **2** (= 2 `msgid`s) |
| PO module listed, key left as `plugin.inlang.icu-messageformat-1` | `✔ Successfully compiled` | **0** | **yes** | **0** |
| correct key, `pathPattern` `./locales/{locale}.po` (no such dir) | `✔ Successfully compiled` | **0** | **yes** | **0** |

The middle row is the half-done state of **this same file's** *Migration: existing ICU-JSON → PO* section: swap the module URL, drop the old key, add the new one. Do two of those three, recompile, and Verify step 1 is green on an app with no translations. The `.po` files are untouched and correct on disk; `settings.json` is valid JSON listing the right module; nothing else in the tree hints at it.

Steps 2 and 3 would catch it at render time. Step 1 exists to catch it earlier and cheaper, and does not. The fix adds the assertion that distinguishes the rows — compiled message modules counted against `msgid`s in the source catalog, which must match and must be `> 0`.

**Deliberately not changed, and flagged in the PR rather than edited:** Verify step 4 claims the production build surfaces "a missing or misconfigured `project.inlang/settings.json`". Both rows above *are* misconfigured settings files and the Vite plugin runs the same compiler, so the claim looks too strong — but testing it needs a full SvelteKit tree, which this finding did not need. Changing a claim on the strength of an inference is exactly item 28's mistake. Left for a follow-up run.

### 2. `@inlang/paraglide-js` 2.25.0 → 2.25.2 — the sequel to last week's `@inlang/sdk` finding

The shipped `dist/` is unchanged apart from the version string. The only substantive line in the two-release diff is `"@inlang/sdk": "^3.0.1"` → `"^3.0.5"`, which pulls in the sequel to the movement recorded on [#71](https://github.com/globalize-now/globalize-skills/issues/71#issuecomment-5580300187) last week.

`@inlang/sdk@3.0.5` (2026-09-11) moves `@lix-js/sdk` **0.15.1 → 0.16.1** and fixes a real concurrency bug that 3.0.4 shipped: 3.0.4's `LixDriver` handed every Kysely caller the **same** `LixConnection`, so two concurrent operations shared one transaction slot. 3.0.5 leases a fresh connection per `acquireConnection()` with an explicit `idle` / `starting` / `active` / `finishing` / `commit-failed` / `closed` state machine, and `snapshotToLix` changes its file insert to `ON CONFLICT (path) DO UPDATE` so restoring a snapshot over an existing file upserts instead of failing on the unique constraint.

### 3. `next-intl` 4.14.2 → 4.14.4 — two bug fixes, no guidance change

Both releases are small and both are `String.prototype.replace` footguns:

```diff
-  result = result.replace(`[${key}]`, value);                      // 4.14.3, middleware/utils
+  result = result.replace(`[${key}]`, () => value);
-  compiled = compiled.replace(new RegExp(regexp, 'g'), replacer);  // 4.14.4, navigation/shared/utils
+  compiled = compiled.replace(new RegExp(regexp, 'g'), () => replacer);
```

A string replacement argument interprets `$&`, `$'`, `` $` `` and `$1`, so a route param value containing `$` was mangled into the compiled pathname. The function form disables that. 4.14.4 also fixes `getBasePath`, which did `windowPathname.replace(pathname, '')` — first-occurrence semantics, wrong when the pathname also appears inside the base path (`/dashboard/dash`) — and now strips only the trailing occurrence.

**Peers byte-identical** across 4.14.2 → 4.14.4 (`next ^12–^16`, `react ^16.8–^19`); `engines` absent in all three. Users on `^4` get both fixes for free. **Nothing to change** — this repo documents neither `getBasePath` nor `$`-bearing route params, and neither fix touches the PO scaffold that [#72](https://github.com/globalize-now/globalize-skills/pull/72) is about. Recorded so the next run does not rediscover it.

### 4. `intl-messageformat` 11.2.15 — a dependency bump with a real fix inside

The package itself is a one-line `package.json` change: `@formatjs/icu-messageformat-parser` `3.5.17` → `3.5.18`. That parser release fixes skeleton hour-cycle resolution — `getDefaultHourSymbolFromLocale` now prefers `Intl.Locale.prototype.getHourCycles()` (the spec method that replaced the `hourCycles` property) over the property, and looks `timeData` up by `language-region` before falling back to region alone. So `{t, time, ::jmm}` picks 12h/24h correctly for locales where the language and the region disagree.

Real, but **not actionable here**: `grep -rn "hourCycle\|hour12\|::jmm"` across `skills/` returns nothing outside a note that ICU date/time skeletons are *not yet runtime-verified* in the paraglide setup. `intl-messageformat@^11` appears on three Vue stacks (`vite-vue-i18n`, `nuxt-vue-i18n`, `quasar-vue-i18n`) and resolves to 11.2.15 with no range change needed.
