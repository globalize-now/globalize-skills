Contents, from the CHANGELOG at tag `v11.4.9`:

| ⚡ | preserve tree-shaking with Vapor | [#2578](https://github.com/intlify/vue-i18n/pull/2578) |
| ⚡ | avoid retaining array message references | [#2571](https://github.com/intlify/vue-i18n/pull/2571) |

Metadata is unchanged across the bump — `engines.node >= 22`, `peerDependencies.vue ^3.0.0`, same dependency set with the three `@intlify/*` siblings moved in lockstep. The skill pins `vue-i18n@^11`, so 11.4.9 is picked up with no edit.

`#2580` was the one worth reading rather than assuming, because "fallback" plus "skips default" is the shape of a thing that changes documented behaviour. It doesn't, for us. The diff is two lines in `packages/core-base/src/fallbacker.ts`:

```diff
       ...(isArray(fallback)
         ? fallback
         : isObject(fallback)
-          ? Object.keys(fallback)
+          ? Object.keys(fallback).filter(locale => locale !== 'default')
           : isString(fallback)
             ? [fallback]
             : [start])
```

The edit is inside the `isObject(fallback)` branch only. Previously a map-form `fallbackLocale` such as `{ en: [], ja: [], default: ['en'] }` contributed the literal string `'default'` to the fallback chain as though it were a locale name; now it is filtered out. The `isString` branch — `fallbackLocale: 'en'` — is untouched.

The skill sets `fallbackLocale` in exactly three places, all string-form:

| File | Line | Value |
|---|---|---|
| `.../vue-i18n/setup.shared.md` | 292 | `fallbackLocale: sourceLocale` |
| `.../vue-i18n/setup.shared.md` | 781 | `fallbackLocale: 'en'` |
| `.../frameworks/nuxt/vue-i18n.setup.md` | 158 | `fallbackLocale: 'en'` |

**No stack the skill generates can reach the changed branch.** Nothing to update, and — noting it explicitly since the temptation exists — nothing to *add* either: the map form is a real vue-i18n feature but the skill has never emitted it, and "the upstream bug is fixed" is not a reason to start.

That file does not exist. `find` across the repo returns nothing by that name, and `git log --all -- skills/globalize-guide/manifest.schema.json` is empty — **it has never existed here.** The `$schema` line dates to `c5c1676` (2026-06-26, #36), so the pointer has been dangling for 60 days.

**Why 114 clean runs didn't see it.** The path assertion this task has reported since the practice began walks `references` objects. `$schema` is at the manifest root, outside any `references` block, so it was never a candidate. Re-run with the predicate widened to every string value ending in `.md` or `.json`:

```
total path-like strings (incl. duplicates): 115
unique:                                      57
unresolved:                    [('/$schema', './manifest.schema.json')]
```

114 + 1 = 115. The single path the narrow check could not see is the single broken one. This is trigger (D) — a clean negative proves only what its pattern covered — but the scope error is in the *traversal*, not the regex, which is a failure mode worth naming separately: **an exhaustive check over a non-exhaustive candidate set reports as exhaustive.**

**Severity: low, filed anyway.** Nothing at runtime reads `$schema`; no user of the skill is affected today. It is worth a ticket because the open queue is about to add constraint fields to this file from four directions — a Node floor (items 1, 12), a Vite peer floor (item 14), an `@swc/core` host floor (item 16), plus `detection.json` work — each optional, each present on some of the 23 stacks and absent on others. There is no JSON-Schema validation anywhere in the repo (`grep -rn "manifest.schema\|ajv\|jsonschema" evals/ .github/` → zero hits; none of the eight `evals/*.sh` scripts check the manifest's shape). Writing the schema is much cheaper before those land than after. Draft at `pending-issues/17-manifest-schema-dangling.md` lays out both options (delete the line vs. write the schema) and recommends the latter.
