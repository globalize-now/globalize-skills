### The path did not rot

Unlike items 0 and 2, item 4's file reference is **correct**. `libraries/next-intl/setup.add-ons.md` exists, and the ESLint content is where the item implies (Add-on 2, L148–228). Two of three audited items had rotted; this one had not. The `#49`/`#50` rules-template restructure deleted `libraries/next-intl/code.md` but left `setup.add-ons.md` alone, which is why item 4 survived it intact.

That is worth recording as a **negative result**: the rot is not universal, and it correlates specifically with items whose paths were touched by the restructure. Item 11 (paraglide `trailingSlash`, cites `sveltekit/paraglide.setup.md` L183–190) remains the last un-audited path-citing item.

### The framing did rot, and that turned out to matter more

Item 4 has always described this as a **staleness** problem: upstream hasn't published in ~22 months, so prune or relegate. Two corrections:

**The staleness figures have drifted** — the item says ~22mo and ~26mo; as of today it is **23.0 months** (`eslint-plugin-next-intl@1.3.1`, 2024-09-18) and **27.1 months** (`@ts-intl/eslint-plugin-ts-intl@2.0.0`, 2024-05-16). Minor.

**But staleness is not the defect.** Reading the section against the actual published tarballs — which no prior run had done, because the item never asked anyone to — turns up **five defects**, and the section is non-functional as written on *both* branches:

| # | Where | Defect |
|---|---|---|
| 1 | L192–193, L205–206 | Emits `next-intl/no-missing-keys` and `next-intl/no-unused-keys`. **Neither rule exists.** The plugin ships exactly three: `no-dynamic-translation-key`, `use-next-intl-link-over-next-link`, `use-router-from-next-intl`. ESLint treats an unknown rule as a **fatal config error**, so the lint run fails outright rather than degrading. |
| 2 | L180–197 | Plugin peers `eslint: ^4 \|\| ^5 \|\| ^6 \|\| ^7 \|\| ^8` — **caps at ESLint 8**, while current stable is **10.8.1** (2026-08-07). Yet L180 detects flat config, calls it "ESLint 9+", and L182–197 emits a flat-config block for it. The section's own primary branch targets a config the plugin does not support; install fails `ERESOLVE` on npm 7+. |
| 3 | L211 → plugin `recommended` | The two **autofixable** rules rewrite imports to `next-intl/link` and `next-intl/client`. Both subpaths were last exported at **2.22.1** and gone by **2.22.2** — verified by walking the exports map across every stable version. All skill paths pin `^4`. A user adopting the documented preset gets `--fix` rewriting correct v4 `createNavigation()` imports into unresolvable specifiers. |
| 4 | L154 | Scope table says "static keys, missing keys, unused keys." Only the first is real; the other two are the same invented pair as Defect 1. Omits both navigation rules — the ones behind Defect 3. |
| 5 | L226 | "Apply the `next-intl` preset specifically." `@ts-intl/eslint-plugin-ts-intl@2.0.0` **exports no configs at all** — its entry point is `__exportStar(require("./rules"), exports)`. No preset exists; its ten rules must be wired individually. |

Verified as **not** a defect, so as not to overclaim: L185's `import nextIntl from 'eslint-plugin-next-intl'` in an ESM flat config is fine — the plugin is CJS `export =`, and Node's interop binds `module.exports` to the default import.

### Severity and mitigation

Raised **low → medium-high**. The honest mitigation is that L159 already sets **"Default recommendation: skip"**, so these paths only execute when a user explicitly opts in against the default. This is not a silent field breakage for the common case, and it is not in the same class as open item 0 (which ships a deprecated call into every user repo via the passive-rule track). But "only fires on opt-in" is a weak defence for instructions that produce a hard lint failure and, in one branch, actively corrupt working code.

### Recommended action changed

From *"prune or move to a legacy section"* to **delete the install paths outright** (L163–228), leaving a short factual note. Fixing the rule names resolves Defect 1 but leaves 2 and 3 standing, and Defect 3 has no fix short of instructing users to disable two of the plugin's three rules. Full reasoning and proposed replacement text in the draft.

**Scope is contained to one file.** Repo-wide grep for the invented rule names returns hits in `setup.add-ons.md` only (L192, L193, L205, L206). No rules template, no `manifest.json` entry, no other reference file touches this surface — so this is a prose-and-snippet edit with **no passive-rule or `templateVersion` implications**. Contrast with the Lingui add-on path, which is healthy: `eslint-plugin-lingui@0.14.0` (2026-06-05, 2.5 months) peers `eslint: ^8.37.0 || ^9 || ^10`.
