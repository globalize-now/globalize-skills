## Finding: `postcss-logical` is configured with an option that was removed three majors ago

**→ draft [`21-postcss-logical-dead-dir-option.md`](./pending-issues/21-postcss-logical-dead-dir-option.md) + [`.patch`](./pending-issues/21-postcss-logical-dead-dir-option.patch). Unfiled — no token. Verified and ready to push.**

`skills/css-i18n/references/css-modules-and-vanilla.md` L225–240 pins `postcss-logical@^9` and then configures it:

```js
require('postcss-logical')({ dir: 'ltr' }),
```

`dir` is not an option of v9. The shipped `dist/index.d.ts` declares the entire surface as `{ ignoreCustomProperties?, blockDirection?, inlineDirection? }`, and the plugin merges the caller's object over its defaults while validating only the two direction keys — so an unknown key is dropped in silence.

`dir` **was** real, in v4 and v5 (both READMEs document `{ dir: 'ltr' }`). **6.0.0 removed it**, per that release's CHANGELOG: *"The plugin now requires block and inline direction to be configured … and no longer introduces `:dir` (major)."* So the snippet pairs a v9 install pin with v5-era option syntax — no version satisfies both halves.

**Measured, not inferred.** `postcss@8.5.6` + `postcss-logical@9.0.1` resolved from the reference's own `^9`, on `.a{ margin-inline-start: 10px; padding-inline: 1px 2px; text-align: start; }`:

| options passed | output | warnings |
|---|---|---|
| `{ dir: 'ltr' }` — as the reference writes it | `margin-left: 10px; padding-left: 1px; padding-right: 2px; text-align: left;` | none |
| `{ dir: 'rtl' }` | **identical** — still `margin-left`, `text-align: left` | none |
| `{ inlineDirection: 'right-to-left' }` — documented | `margin-right: 10px; padding-right: 1px; padding-left: 2px; text-align: right;` | none |
| no options at all | identical to `{ dir: 'ltr' }` | none |

The second row is the damaging one: a reader of a **CSS internationalisation** reference who copies this and changes `'ltr'` to `'rtl'` — the obvious move — gets LTR physical properties, silently, in a mis-mirrored stylesheet.

**What is *not* wrong:** the `require()` of this ESM-only package is fine. v9 declares `engines.node >= 20.19.0`, where `require(esm)` works; verified loading on Node 22.23.2. Only the option is wrong. Saying so matters — "the snippet is broken" would have been a bigger and false claim.

The draft also fixes the reason the option existed: v5 could emit `:dir(ltr)`/`:dir(rtl)` pairs, **6.0.0 removed that**, and v9 flattens each logical property to one configured direction and drops the original. For an RTL-capable site that is a consequence worth one sentence, which the reference currently does not carry.

## Finding 2 answered, not opened: the (F) head

Yesterday's designated head: *does the `next-intl` `experimental.messages` PO loader have the same dot-path collision defect #88 fixes in the `vue-i18n` loader?*

**No — and it cannot.** The two loaders are structurally different, which is the part worth writing down:

- The **vue-i18n** loader is **authored by this skill** (`vite/vue/vue-i18n.setup.md` L95–105). It builds a nested object with a `setByPath` walk whose guard is `if (typeof node[p] !== 'object' || node[p] === null) node[p] = {}` — that is the line #88 fixes, and it is where a string at `A.b` gets clobbered by `{}` for `A.b.c` (or the reverse).
- The **next-intl** codec is **upstream** — `BuiltInPoCodec` wrapping `@eloqnt/format-po`, resolved through the same `formats` registry the Turbopack rule and the Webpack rule both use (confirmed in `plugin.cjs`: both call `getFormatExtension(pluginConfig.experimental.messages.format)`). It never nests.

Settled by running the codec directly on a catalog with a deliberate collision, rather than by a Next.js build:

```
id='HomePage.greeting'        message='Hello'
id='A.b'                      message='parent value'
id='A.b.c'                    message='child value'
id='navigation.Common.close'  message='Close'
id='Common.close'             message='Close (dialog)'
```

Flat array, five entries, every `id` a string, no nested object anywhere in the output. `A.b` and `A.b.c` both survive. **No finding, and none to file.**

Two things fell out of reading that codec, both already accounted for:

- **The layout-mode detector.** `@eloqnt/format-po` picks one of three modes from the PO header: `id-msgid` (`X-Crowdin-SourceKey: msgstr`, the old next-intl layout), `key-msgctxt` (`X-Message-Key: msgctxt`, the current one), or `gettext` when neither header is present. `BuiltInPoCodec` hard-errors on the first — but **only** on the literal `X-Crowdin-SourceKey: msgstr` header, which skill-authored catalogs do not carry, so they read as `gettext` and the skill's dot-path-in-`msgid` convention resolves as intended. I checked this specifically because "next-intl now rejects the layout this skill teaches" would have been today's headline, and it is **not true**. Worth recording as a near-miss: item **57**.
- **`msgctxt` prefixes the key.** In `gettext` mode the id is `msgctxt + '.' + msgid` — so `msgctxt "navigation"` + `msgid "Common.close"` resolves as `navigation.Common.close`, not as a disambiguated `Common.close`. That is exactly the subject of open PR **#67** ("correct `msgctxt` semantics and gate PO catalogs on 4.x"), a draft for three weeks and three days. Corroborating evidence for #67, not a new finding — and one more reason it needs a human.
