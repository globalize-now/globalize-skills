|---|---|---|---|
| `@lingui/vite-plugin` | `^6` | `^6.3.0 \|\| ^7 \|\| ^8` | **required** |
| `@vitejs/plugin-react-swc` | `^4` | `^4 \|\| ^5 \|\| ^6 \|\| ^7 \|\| ^8` | required |
| `@vitejs/plugin-react` | `^5` | `^4.2.0 \|\| ^5 \|\| ^6 \|\| ^7 \|\| ^8` | required |
| `@intlify/unplugin-vue-i18n` | `^11` | `^6 \|\| ^7 \|\| ^8` | *optional* |
| `@inlang/paraglide-js` | `^2` | `>=5.0.0` | *optional* |

### Why this outranks item 12

An `engines` mismatch is an `EBADENGINE` **warning** on npm. An unsatisfiable **required peer** is `ERESOLVE` — a hard install failure on npm ≥ 7 and on pnpm's default strictness; warn-only on Yarn Berry and bun, which is worse rather than better, because there the plugin loads against an unsupported Vite and fails later at build. And §2.0 says "If the install command fails … stop the run with the error", so a Vite 5 project gets a raw npm error at the point of maximum invested effort.

The fix belongs in the same change as item 12 — `viteVersion` in `detection.json`, gate after §1.5 resolves the variant (a Vite 5 project is fine on vue-i18n or Paraglide and broken on Lingui), range derived from the manifest rather than written into ten files. One extra note for the message: **`@lingui/vite-plugin@^5` still accepts Vite 3–8** and its line runs to 5.9.5 (2026-04-06, two weeks *after* 6.0.0 shipped), so "upgrade Vite ≥ 6.3, *or* pin `@lingui/vite-plugin@^5`" is a materially better stop than "upgrade Vite."

Draft: `pending-issues/14-vite-peer-floor-ungated.md`.

## Finding 3 (new item 15, medium-high) — open item 3's hazard went live eight days ago

Open item 3 — "re-verify `@lingui/swc-plugin` swc_core ABI compat through 6.6.0" — has been open since 2026-04-25 and never audited. It is now answerable.

`@lingui/swc-plugin` ships a prebuilt Wasm (`"main": "./lingui_macro.wasm"`), loadable only by a host whose swc_core matches its build ABI:

| | Source | `@swc/core` |
|---|---|---|
| `@lingui/swc-plugin@6.6.0` (2026-07-24) | its `devDependencies` at build time | `^1.15.33` |
| `@vitejs/plugin-react-swc@4.3.3` (the host) | its `dependencies` | `^1.15.46` |

`^1.15.46` resolves to `<2.0.0`. `@swc/core` published **1.16.0 on 2026-08-14** and **1.16.1 on 2026-08-19**. A fresh install *today* puts the host on 1.16.1 and the plugin's Wasm on the 1.15 line.

**Five stacks exposed, of which four are explicit.** `tanstack-start-swc-lingui`, `remix-swc-lingui`, `react-router-framework-swc-lingui` and `webext-swc-lingui` install both packages (`manifest.json` L127, 163, 202, 366). `vite-swc-lingui` (L70) installs `@lingui/swc-plugin@^6` and inherits the host from whatever `@vitejs/plugin-react-swc` the project already has — same exposure, one less thing the manifest controls. `nextjs-app-router-lingui` (L11) pairs against Next's bundled SWC and is out of scope here.

**npm cannot warn about this.** `@lingui/swc-plugin@6.6.0` declares `peerDependencies: {"@lingui/core": "5 || 6"}` only. `@swc/core` and `next` appear in `peerDependenciesMeta` **with no corresponding `peerDependencies` entries** — which is a no-op. There is no `engines` field either. No package manager at any strictness setting can flag it.

**What I did not verify, deliberately:** whether swc_core's plugin ABI actually broke between the 1.15 and 1.16 lines. swc bumps plugin ABI on its own cadence, not on every minor, and that cannot be read out of registry metadata. Someone should check <https://plugins.swc.rs> for the 6.6.0 / 1.16.x pair before treating this as a live break. If the ABI held, the issue reduces to the tripwire below. I would rather hand over a sharp question than a confident guess.
