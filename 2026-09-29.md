## Finding: `1.16.12` moved the native addon behind a validated materialization cache

**→ draft [`24-swc-core-1-16-12-native-binding-cache.md`](./pending-issues/24-swc-core-1-16-12-native-binding-cache.md). Unfiled — no token. Issue-shaped, not a PR.**

`@swc/core-linux-arm64-gnu` unpacked sizes, same `fileCount` of 4 throughout: `1.16.0` 32 731 319 → `1.16.1` 32 735 415 → `1.16.2` 33 325 239 → **`1.16.12` 10 664 616**. The shipped `.node` is a stub; `dlopen` materializes the real addon into a cache directory and validates it first:

```
Error: SWC native addon: validate cache root <path>: cache root has a parent writable
by another user without trusted sticky protection. … check SWC_NATIVE_BINDING_CACHE
and directory permissions for materialization failures.   code: 'ERR_SWC_NATIVE_CACHE'
```

The predicate is about **ancestors**. On this machine `/` is `drwxr-xr-x nobody:nogroup`, so all four candidate roots are rejected — default `$HOME/.cache`, `/tmp` and `/var/tmp` (both `drwxrwxrwt`, i.e. carrying the sticky bit the message names as the exemption), and a fresh `0700` directory in the project. The `SWC_NATIVE_BINDING_CACHE` escape hatch the error names cannot reach an ancestor the caller does not own, and "make either directory writable" does not describe the problem — the directory is writable; it is owned by the wrong uid.

**Measured, one machine, one probe** — `@lingui/swc-plugin@6.7.0`, `` t`Hello ${name}` `` through `transform()` with the Wasm plugin:

| host | `swc_core` | result |
|---|---|---|
| `@swc/core@1.16.2` | 78.0.0 | **OK** — `$_i18n._({ id: "OVaF9k", message: "Hello {name}", values: { name } })` |
| `@swc/core@1.16.12` | 81.0.1 | **`Failed to load native binding`** / `ERR_SWC_NATIVE_CACHE`, thrown from `require('@swc/core')` |

The second row is a *load* failure, upstream of any plugin. **Whether the plugin still runs on a `swc_core@81.0.1` host is unmeasured** — that host cannot be loaded here at all. That is the one question under the draft's `## Needs a human`, and it is one `npm i` away on an ordinary machine.

**`npm install` exits 0.** `postinstall.js` detects the load failure and installs `@swc/wasm` — present in the 1.16.12 tree, **absent** in the 1.16.2 tree where the native load worked. It is never used: `index.js` L76–93 wires the fallback inside a `try/catch`, but **L66** (`var binding_1 = require("./binding")`, added for the `experimental_newMangleNameCache` re-export) throws at module scope first. L66 is byte-identical in 1.16.2, so the unreachable fallback is pre-existing and this release is what makes it bite. Net effect for a user of these skills: a green install and a `vite build` that dies on cache-root permissions, with nothing in the message about SWC plugins or i18n.

**Exposure.** `@swc/core` is not pinned anywhere in `skills/`. `@vitejs/plugin-react-swc` `4.2.3`–`4.3.1` depend on `@swc/core@^1.15.11` and `4.3.2`–`4.3.3` on `^1.15.46`; **both admit 1.16.12**. Five stacks plus `lovable-i18n` resolve it that way. And #69's remedy sentence — `npm install -D '@swc/core@^1.15'` — resolved to `1.16.1` when it was written and resolves to `1.16.12` now.

**Why an issue and not a PR** (the draft argues it at length): the obvious change is a backwards pin, which is exactly what #69 spends its diff arguing against and what withdrawn draft 15 got wrong with the sign flipped; the blast radius (how common a non-root-owned `/` or mount ancestor is) is not establishable from one sandbox; and the likely real fix is an upstream one-liner guarding `index.js:66`, not a skills change.
