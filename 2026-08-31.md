### What this overturns

1. **The floor is `@swc/core` ≥ 1.15.0.** Both PRs said ≥ 1.16.0. Every `1.15.x` rung passes.
2. **The `swc_ecma_ast`-match rule is refuted in both directions at once.** The widest gap tested works (18.0.0 host / 29.0.0 plugin); the narrowest gap tested fails (17.0.0 / 19.0.0). It has no predictive power, and as an instruction it was unfollowable — the same defect as the `swc_core`-match rule it replaced, one level along.
3. **Plugin version is not the variable.** `6.0.0` and `6.7.0` behave identically at both ends of the boundary. So "pin the plugin backwards" is not a remedy for a below-floor host, in any of the copies that offered it.
4. **`@vitejs/plugin-react-swc >= 4.2.3` *is* a sufficient host proxy** — `4.2.3`-`4.3.1` declare `@swc/core@^1.15.11`, `4.3.2`+ declare `^1.15.46`, and both range floors clear 1.15.0. Yesterday's claim that no version of it suffices, `4.3.3` included, was the operational half of the error and would have made the skills warn about working setups. The genuinely insufficient range is `4.0.0`-`4.2.2` (`^1.13.5`) and the whole of `3.x` (down to `^1.3.30`) — a real distinction, now the one the files state.
5. **A `3.x` project needs no major bump.** `@swc/core` is a plain dev dependency and every `3.x` range is a caret on `1.x`, so it already admits `1.15`+. Verified: `@vitejs/plugin-react-swc@3.11.0` with `@swc/core@1.16.1` builds and transforms. `npm install -D '@swc/core@^1.15'` is a far smaller ask than forcing `@vitejs/plugin-react-swc@^4`, and it is now the first remedy in every corrected copy.
6. **The observed failure message is `failed to invoke plugin on 'Some("<file>")'`**, with the build reporting `0 modules transformed`. Not `failed to run Wasm plugin transform` (present in the binary, but not what this path prints) and — still, unchanged from yesterday — not `swc_core version mismatch`, which the binary does not contain at all. That finding was the one thing yesterday got right and it survives intact.

### What survives from yesterday

The **source** reading was accurate and is unchanged: `is_transform_schema_compatible()` compares an AST schema version hardcoded to `1` on both sides, marked `// TODO: this is incomplete`, so no ordered check discriminates anything. That is why a below-floor host fails inside the transform rather than at load. The error was not in reading the runner; it was in what got substituted for the guard that was found missing.

### How the error was shaped

Yesterday's run correctly demolished the `swc_core`-match rule, then put a *structurally identical* rule in its place — same shape, different crate — and shipped it into six files as the load-bearing number, on source evidence that could not distinguish it from the truth. Item 27 was opened, in the same report, on exactly this: *a claim is sourced, but not to the thing being claimed.* It described the error it was itself making. The rule it produced is right and stands; what it needed and did not have was the step that turns a mechanism into a prediction, which is running the thing.

**Item 16 and item 27 both close today.** Item 28 is new and is the general form.
